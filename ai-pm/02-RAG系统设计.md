## Q7: 你们的 RAG 系统是怎么设计的？为什么自建而不是用钉钉 AI？

> **一句话**：从 10 个钉钉知识库自动同步 → 4 策略分块 → bge-small 嵌入 → pgvector + FTS5 混合检索 → RRF 融合 → LLM 流式生成。自建是因为钉钉 AI 跨不了 workspace、检索质量黑盒、无法融合业务数据。

### 系统架构全景

```
钉钉知识库（10 个工作区）
  → 自动同步（文档树 → 下载 → 解析为 Markdown）
  → 智能分块（4 策略自适应：技术文档/会议/表格/文本）
  → 嵌入向量化（bge-small-zh-v1.5, 512d → pgvector）
  → 混合检索（FTS5 关键词 + 向量语义 → RRF 融合）
  → LLM 生成回答（检索 chunk + 用户问题 → SSE 流式返回）
```

一句话：**用户用自然语言提问，系统自动从海量企业文档中找到相关片段，生成准确回答，附带来源引用。**

### 为什么不用钉钉 AI？（五个维度对比）

| 维度 | 钉钉 AI | 自建 RAG |
|------|---------|----------|
| 跨知识库聚合 | ❌ 单 workspace | ✅ 10 库统一检索 |
| 检索质量可控 | ❌ 黑盒，等平台更新 | ✅ 全链路可控，A/B 实验驱动 |
| 业务数据融合 | ❌ 仅钉钉文档 | ✅ 知识库 + TB 任务数据融合 |
| 数据安全 | ⚠️ 经钉钉服务器 | ✅ 内网私有化 |
| 长期成本 | 高（按量付费） | 低（自有 infra） |

核心痛点举例：用户问"导航精度和到点自学习的关系"，答案散落在 3 个不同 workspace 里，钉钉 AI 只能在单个 workspace 内搜。

### 为什么不用纯工程化方案？

| 方案 | 为什么不够 |
|------|-----------|
| **纯关键词搜索** | 用户不会精确概括关键词。"车走偏了怎么回事"和文档里的"AGV 走偏 轮速差 编码器"词面完全对不上 |
| **结构化数据库** | 企业知识天然非结构化——PRD、会议纪要、设计文档不可能统一建模 |
| **人工 Wiki** | 10 个知识库持续更新，手动维护不可接受 |
| **规则匹配** | 问题空间开放式，无法穷举。维护成本随知识增长线性上升 |

### 工程和 AI 不是对立，是互补

```
工程侧：FTS 精确匹配 | 4策略自适应分块 | RRF 融合排序 | 钉钉 API 文档同步
AI 侧： bge-small 语义检索 | LLM 综合生成回答
```

**面试金句**：
> "钉钉 AI 是通用搜索，我们做的是领域知识引擎。前者告诉你'哪里可能有答案'，后者直接给你答案。"
> "工程化方案让用户适应系统，AI 让系统适应用户。这是范式选择，不是技术选型。"

### 精度-召回优化策略

```
当前：检索 top-20 → 融合 → 取 top-8
  → 保精度（宁可少，不要错）

对照试验：用 Recall@5 / MRR / nDCG 三项指标
  → 量化评测，不是拍脑袋

加 reranker（计划中）：
  → 先粗召回 20 条（保召回）
  → 再精排到 8 条（提精度）
  → 不牺牲召回的提精度
```

> 精度和召回率的概念解释见 [01-AI技术基础 Q5](../01-AI技术基础.md#q5-精度和召回率在-rag-系统里怎么理解和平衡)

## Q8: 模型调用链路是怎样的？数据安全吗？

> **一句话**：Flask 后端 → one-api 内部代理 → DeepSeek 等外部模型服务商。不发送源代码，只发送知识库 markdown 文档片段。可逐步加固到私有化部署。

### 调用链路

```
用户请求 → Flask 后端
  → 检索本地知识库（MySQL + pgvector）
  → 拼接 prompt（system prompt + 检索文档片段 + 用户问题）
  → HTTP POST → one-api 代理（内部部署）
  → 转发到模型服务商（DeepSeek）
  → SSE 流式返回
```

关键参数：
- 模型：`deepseek-v4-flash`
- Temperature：0.3
- Max tokens：4096
- one-api 统一代理，API key 集中管理

### 数据安全逐环节分析

| 环节 | 数据暴露 | 风险 | 现状 |
|------|---------|------|------|
| 知识库文档内容 | 作为 prompt 发送给 LLM | ⚠️ 中 | 仅 markdown 文档片段 |
| 源代码 | **不发送** | ✅ 低 | - |
| TB 任务数据 | 检索到的标题/状态 | ⚠️ 中 | 限检索范围 |
| 用户身份 | 不发送给 LLM | ✅ 低 | - |
| API Key | 存储于 config.json | 🔴 高 | ⚠️ 生产需改用密钥管理 |

### 加固路径

```
当前：文档内容 → one-api 代理 → 外部模型服务商
升级1：one-api 挂私有化部署的 DeepSeek 开源模型，数据不出内网
升级2：敏感文档脱敏/摘要后再发送
升级3：按知识库分级——机密走本地，普通走云端
```

**面试回答模板**：
> 我们通过 one-api 内部代理统一管理模型调用。目前风险可控——不发送源代码，只发送知识库 markdown 文档。如果安全要求更高，可以在 one-api 后面挂私有化部署的开源模型，数据完全不出内网。这是一个可以逐步加固的过程。

## Q9: 上下文窗口溢出了怎么办？

> **一句话**：当前做简单截断（8000 token 上限）。最优方案是加 reranker 精排——从 20 条粗召回中精挑 8 条，保证进 prompt 的都是最相关的。

### 当前处理

```python
total_tokens = 0
for r in results:
    tk = r.get("token_count") or len(content) // 2
    if total_tokens + tk > _MAX_CONTEXT_TOKENS:
        break  # 超限即丢弃
    parts.append(content)
    total_tokens += tk
```

问题：后面的 chunk 直接丢弃，8000 token 对 deepseek-v4 过于保守。

### 五种处理策略对比

| 策略 | 做法 | 优劣 |
|------|------|------|
| **Rerank 精排** ⭐推荐 | 粗召回 20 → reranker 精排到 8 | 保证最相关内容进 prompt |
| Summary 压缩 | LLM 先摘要再拼接 | 保信息但多一次 LLM 调用 |
| 动态窗口 | 按模型实际能力调上限 | 利用大窗口，减少截断 |
| 分层检索 | 先搜摘要→命中后加载全文 | 类似"目录→正文" |
| Map-Reduce | 分批生成→合并 | 适合超长文档 |

你们的对照试验加 reranker，本身就是对上下文利用率的优化。

## Q10: 端到端响应速度怎么样？怎么优化？

> **一句话**：当前 2-10 秒。检索 ~200-500ms，LLM 生成是主要耗时。已做 SSE 流式输出，用户可边等边看。缓存是下一步。

### 延迟构成

| 环节 | 耗时 | 优化空间 |
|------|------|---------|
| SQLite FTS 关键词 | ~10-50ms | 小 |
| pgvector 向量检索 | ~100-300ms | 加索引 |
| RRF 融合 | ~5ms | 小 |
| LLM 首 token | ~500-2000ms | 流式已做 |
| LLM 完整生成 | 2-10s | 流式已做 |

### 已做优化
- SSE 流式输出：用户不用等全部生成
- 状态提示："检索本地向量知识库" → "调用模型生成回答"

### 待做优化
- 检索缓存：相同 query 秒回
- 预加载 embedding 模型：减少首次延迟

**面试话术**：
> "当前端到端 2-10 秒，SSE 流式让用户边等边看。后续计划加检索缓存，相同 query 秒级返回。"

## AI 知识库的 6 个应用场景

同一套 RAG 基础设施，覆盖多个场景：

```
                   AI 知识库核心能力
                   文档同步 → 分块 → 嵌入 → 检索 → 生成
                          │
      ┌──────┬──────┬─────┼─────┬──────┬──────┐
      ▼      ▼      ▼     ▼     ▼      ▼      ▼
   内部问答  现场   新人   售前  项目   测试   客户
          排障   培训   应答  复盘   生成   支持
```

### 场景 1：现场问题处理

> 现场工程师："伺服驱动器报错 AL-013，怎么处理？"
>
> → 检索「伺服报错汇总」→ 错误码定义 + 标准处理流程
> → 检索技术文档 → 补充背景
> → 检索复盘文档 → 历史处理经验
> → 生成结构化回答：原因 → 排查 → 方案 → 预防

**价值**：减少对资深工程师依赖，降低停机时间，知识可沉淀。

### 场景 2：研发新人 Onboarding

> 新人："导航模块的整体架构是怎样的？"
>
> → 检索设计文档 → 架构描述 + 模块划分
> → 检索 Roadmap → 当前开发重点
> → 检索复盘 → 历史踩坑记录
> → 生成入职学习路径建议

**价值**：从"老员工口口相传"变成"自助式知识获取"，缩短上手周期。

### 场景 3：跨部门信息对齐

> 售前："我们的 AGV 支持哪些导航方式？精度指标是多少？"
>
> → 检索技术文档 → 激光/二维码/磁导航/视觉 SLAM 及精度数据
> → 检索产品信息门户 → 对客宣传标准表述
> → 生成可直接用于客户提案的回答

**价值**：打破部门信息壁垒，售前不需要每次都找研发确认。

### 场景 4：项目复盘与决策支持

> Leader："Q1 导航模块的主要问题是什么？解决了吗？"
>
> → 检索复盘文档 → 问题清单
> → 检索版本更新日志 → 追踪修复状态
> → 检索 Roadmap → 遗留项
> → 生成问题闭环状态报告

**价值**：从"翻十几个文档手动拼凑"到"一句话查询"。

### 场景 5：客户支持与售前应答

> 客户："调度系统支持多少台 AGV 同时调度？"
>
> → 基于设计文档和测试报告给出准确数字 + 出处引用

**价值**：响应快、回答有据可依、降低售前对研发的依赖。

### 场景 6：自动化测试用例生成

> 测试："根据导航控制器接口文档生成回归测试 checklist"
>
> → 检索接口协议 → 提取接口定义
> → 检索性能指标 → 提取验收标准
> → 生成结构化测试用例

**价值**：从文档到测试用例的自动化转换。

## 面试话术汇总

### 30 秒总述

> management-system 里我做了企业知识库问答系统，用户用自然语言问问题，系统从 9 个钉钉知识库中检索相关内容，用大模型生成带来源引用的回答。
>
> 不用工程化方案是因为企业知识天然非结构化——PRD、会议纪要、表格没法用 SQL 或规则穷举。不用钉钉 AI 是因为需要跨 workspace 检索和融合业务数据。这套能力不只是内部问答——现场排障、新人培训、售前应答、项目复盘都能用，一套基础设施覆盖 6 个场景。

### 关键金句

1. "工程化方案让用户适应系统，AI 让系统适应用户。"
2. "钉钉 AI 是通用搜索，我们做的是领域知识引擎。"
3. "真正的务实方案不是选 AI 还是选工程，而是每个环节用最合适的工具。"
4. "同一套 RAG 基础设施，换个前端就是不同的产品——这是 AI PM 该有的复用思维。"
