# AI 知识库核心用途

> 覆盖面试高频两问：为什么不用工程化方案？为什么不用钉钉自带 AI？以及这个 AI 知识库到底能做什么？

---

## 一、RAG 系统是什么

management-system 的 RAG 模块是一个**企业内部知识库问答系统**：

```
钉钉知识库（10 个工作区）
  → 自动同步（文档树 → 下载 → 解析为 Markdown）
  → 智能分块（4 策略自适应：技术文档/会议/表格/文本）
  → 嵌入向量化（bge-small, 512d → pgvector）
  → 混合检索（FTS 关键词 + 向量语义 → RRF 融合）
  → LLM 生成回答（检索 chunk + 用户问题 → 流式返回）
```

一句话：**用户用自然语言提问，系统自动从海量企业文档中找到相关片段，生成准确回答，附带来源引用。**

## 二、为什么不用工程化方案？

### 2.1 评估过的四种方案

| 方案 | 为什么不够 |
|------|-----------|
| **纯关键词搜索** | 用户不会精确概括关键词。"车走偏了怎么回事"和文档里的"AGV 走偏 轮速差 编码器"词面上完全对不上 |
| **结构化数据库** | 企业知识天然非结构化——PRD、会议纪要、设计文档不可能统一建模。强行结构化会丢失上下文 |
| **人工 Wiki** | 9 个知识库持续更新，手动维护成本不可接受。时效性和覆盖率都保证不了 |
| **规则匹配** | 问题空间是开放式的，无法穷举。规则维护成本随知识增长线性上升 |

### 2.2 本质区别

| 特征 | 工程化方案 | RAG + LLM |
|------|-----------|-----------|
| 数据是非结构化的 | ❌ 需要人工结构化 | ✅ 直接消费原始文本 |
| 用户查询是开放式的 | ❌ 只能匹配关键词 | ✅ 语义理解 |
| 知识在持续更新 | ❌ 人工同步滞后 | ✅ 自动同步管线 |
| 需要综合多文档 | ❌ 做不到 | ✅ LLM 推理合成 |

### 2.3 工程和 AI 不是对立，是互补

当前架构是**工程和 AI 的混合**，每个环节用最合适的工具：

```
工程侧：FTS 精确关键词匹配  | 4策略自适应分块 | RRF 融合排序 | 钉钉 API 文档同步
AI 侧： bge-small 语义检索    | LLM 综合生成回答
```

**这是系统工程，不是堆 AI。** 精确匹配用工程，语义理解用 AI，排序融合用经典算法，生成用 LLM。

## 三、为什么不用钉钉自带 AI？

### 3.1 五个维度的评估

| 维度 | 钉钉 AI | 自建 RAG |
|------|---------|----------|
| 跨知识库聚合 | ❌ 单 workspace | ✅ 9 库统一检索 |
| 检索质量可控 | ❌ 黑盒 | ✅ 全链路可控 |
| 业务数据融合 | ❌ 仅钉钉文档 | ✅ 知识库 + TB 数据 |
| 数据安全 | ⚠️ 经钉钉服务 | ✅ 内网私有化 |
| 长期成本 | 高（按量付费） | 低（自有 infra） |

**核心问题 1：跨知识库。** 用户问"导航精度和到点自学习的关系"，答案散落在 3 个不同 workspace 里，钉钉 AI 只能在单个 workspace 内搜。

**核心问题 2：黑盒不可控。** 不知道它用的什么 embedding、什么 chunking 策略、召回了几条。搜不准时只能等钉钉更新——自建系统可以立即定位问题、A/B 实验、数据驱动迭代。

**核心问题 3：无法融合业务数据。** "小明这周做了什么导航相关工作？"——需要同时查 TB 任务（工时）+ 知识库（文档），钉钉 AI 做不到。

### 3.2 金句

> "钉钉 AI 是通用搜索，我们做的是领域知识引擎。前者告诉你'哪里可能有答案'，后者直接给你答案。"

> "工程化方案让用户适应系统，AI 让系统适应用户。这是范式选择，不是技术选型。"

## 四、AI 知识库能做什么（6 个场景）

同一套 RAG 基础设施，覆盖多个场景：

```
                   AI 知识库核心能力
                   文档同步 → 分块 → 嵌入 → 检索 → 生成
                          │
      ┌──────┬──────┬─────┼─────┬──────┬──────┐
      ▼      ▼      ▼     ▼     ▼      ▼      ▼
   内部问答  现场   新人   售前  项目   测试   客户
          排障   培训   应答  复盘   生成   支持
```

### 场景 1：现场问题处理

> 现场工程师："伺服驱动器报错 AL-013，怎么处理？"
>
> → 检索「伺服报错汇总」→ 错误码定义 + 标准处理流程
> → 检索技术文档 → 补充背景
> → 检索复盘文档 → 历史处理经验
> → 生成结构化回答：原因 → 排查 → 方案 → 预防

**价值**：减少对资深工程师依赖，降低停机时间，知识可沉淀。

### 场景 2：研发新人 Onboarding

> 新人："导航模块的整体架构是怎样的？"
>
> → 检索设计文档 → 架构描述 + 模块划分
> → 检索 Roadmap → 当前开发重点
> → 检索复盘 → 历史踩坑记录
> → 生成入职学习路径建议

**价值**：从"老员工口口相传"变成"自助式知识获取"，缩短上手周期。

### 场景 3：跨部门信息对齐

> 售前："我们的 AGV 支持哪些导航方式？精度指标是多少？"
>
> → 检索技术文档 → 激光/二维码/磁导航/视觉 SLAM 及精度数据
> → 检索产品信息门户 → 对客宣传标准表述
> → 生成可直接用于客户提案的回答

**价值**：打破部门信息壁垒，售前不需要每次都找研发确认。

### 场景 4：项目复盘与决策支持

> Leader："Q1 导航模块的主要问题是什么？解决了吗？"
>
> → 检索复盘文档 → 问题清单
> → 检索版本更新日志 → 追踪修复状态
> → 检索 Roadmap → 遗留项
> → 生成问题闭环状态报告

**价值**：从"翻十几个文档手动拼凑"到"一句话查询"。

### 场景 5：客户支持与售前应答

> 客户："调度系统支持多少台 AGV 同时调度？"
>
> → 基于设计文档和测试报告给出准确数字 + 出处引用

**价值**：响应快、回答有据可依、降低售前对研发的依赖。

### 场景 6：自动化测试用例生成

> 测试："根据导航控制器接口文档生成回归测试 checklist"
>
> → 检索接口协议 → 提取接口定义
> → 检索性能指标 → 提取验收标准
> → 生成结构化测试用例

**价值**：从文档到测试用例的自动化转换。

## 五、面试话术汇总

### 30 秒总述

> management-system 里我做了企业知识库问答系统，用户用自然语言问问题，系统从 9 个钉钉知识库中检索相关内容，用大模型生成带来源引用的回答。
>
> 不用工程化方案是因为企业知识天然非结构化——PRD、会议纪要、表格没法用 SQL 或规则穷举。不用钉钉 AI 是因为需要跨 workspace 检索和融合业务数据。这套能力不只是内部问答——现场排障、新人培训、售前应答、项目复盘都能用，一套基础设施覆盖 6 个场景。

### 关键金句（可单独使用）

1. "工程化方案让用户适应系统，AI 让系统适应用户。"
2. "钉钉 AI 是通用搜索，我们做的是领域知识引擎。"
3. "真正的务实方案不是选 AI 还是选工程，而是每个环节用最合适的工具。"
4. "同一套 RAG 基础设施，换个前端就是不同的产品——这是 AI PM 该有的复用思维。"
