## Q11: 多 Skill 和 MCP 并存时，AI 会不会选错工具？

> **一句话**：会的。根本原因是 LLM 的"工具选择"是语义匹配，不是逻辑判断。解决靠三点：统一入口、互斥触发条件、失败反问兜底。

### 你们的现状

**Skills（6 个 SKILL.md）**：server_ops、keyword_extract、tb_analysis、perf_analysis、tb_create、kb_qa

**MCP Tools（4 个）**：get_user_task_context、create_teambition_task、search_knowledge_base、get_workhour_summary

### 三个典型问题

**问题 1：功能重叠，AI 可能选错入口**

| 用户想做的事 | 可以走的路 | 风险 |
|-------------|-----------|------|
| 创建任务 | SKILL.md curl **vs** MCP tool | 走 curl 可能绕过 MCP 校验 |
| 搜知识库 | SKILL.md curl **vs** MCP tool | 返回格式不一致 |
| 分析任务 | tb_analysis **vs** perf_analysis | 边界模糊 |

**问题 2：Skill 描述模糊，触发条件重叠**

用户说"帮我看看任务情况"——tb_analysis 和 perf_analysis 都可能触发。

**问题 3：双轨制造成不确定性**

同一能力两个入口（curl vs MCP），AI 行为取决于它先看到哪个。

### 解决方案

| 方案 | 做法 | 类型 |
|------|------|------|
| **A. 统一入口** ⭐推荐 | MCP 承载可执行工具，SKILL.md 只负责 workflow | 治本 |
| B. 互斥条件 | 每个 skill 加"触发条件"和"不触发条件" | 治标 |
| C. 意图分类前置 | 先分类意图 → 再加载对应 skill 组 | 架构优化 |
| D. 动态加载 | AI 自主判断何时加载哪个 skill（Claude Code 自带能力） | 长线 |

### Agent 工具设计的五条黄金法则

```
1. 一个能力，一个入口 → 不要同时有 curl 版和 MCP 版
2. 触发条件要互斥 → 用户一句话只命中一个 skill
3. 越少越好 → 5 个精准 > 20 个模糊
4. 描述比实现重要 → AI 靠描述选工具
5. 失败要有兜底 → 不确定时反问，不硬选
```

**面试回答模板**：
> 当前确实存在功能重叠风险——创建任务有 curl 和 MCP 两种方式。解决方案是"一个能力一个入口"：让 MCP 统一承载可执行工具，SKILL.md 只负责工作流指导。同时 skill 描述要加互斥触发条件。Agent 工具设计的核心原则是：5 个精准的 skill 比 20 个模糊的好得多，AI 靠描述选工具，描述质量决定选择质量——这不是技术问题，是产品设计问题。

## Q12: n8n / Coze / Dify 有什么区别？各适合什么场景？

> **一句话**：n8n 是从传统自动化延伸 AI，Coze 是零代码 AI Bot 平台，Dify 是开源 LLMOps 全链路平台。选型取决于你的场景是"连接 SaaS"、"快速搭 Bot"、还是"精细控制 RAG"。

### 一句话定位

| 平台 | 定位 | 类比 |
|------|------|------|
| **n8n** | 开源自动化引擎，从传统工作流向 AI 延伸 | 开源的 Zapier + AI |
| **Coze** | 字节的低代码 AI Bot 搭建平台 | AI 时代的"人人都是开发者" |
| **Dify** | 开源 LLM 应用开发平台 | 开源的 GPTs + RAG 引擎 |

### 核心差异全景

| 维度 | n8n | Dify | Coze |
|------|-----|------|------|
| **起源** | 传统工作流自动化 | LLM 应用开发 | AI Bot/Agent 搭建 |
| **目标用户** | 技术型运营/DevOps | 开发者/技术 PM | 非开发者/运营 |
| **开源** | ✅ Fair-code | ✅ Apache 2.0 | ❌ 闭源 |
| **部署** | 自部署 + Cloud | 自部署 + Cloud | Cloud Only |
| **AI 能力** | 后来追加（AI 节点） | 原生集成（RAG/Agent） | 原生集成（Plugin/Bot） |
| **生态** | 400+ 集成节点 | 模型/工具/数据集生态 | 插件商店 + Bot 商店 |
| **学习曲线** | 中（传统自动化思维） | 中（LLM 应用思维） | 低（拖拽 + 对话） |
| **中国本地化** | 一般 | 良好（中国团队） | 极好（字节出品） |

### 三选一决策框架

```
需要连接大量外部 SaaS？ → n8n（连接器生态最强）
需要在钉钉/飞书/微信发布 AI Bot？ → Coze（字节生态 + 多渠道）
需要做企业内部 RAG 系统？ → Dify（RAG 全链路最完整）
需要私有化部署？ → n8n 或 Dify（都开源）
团队没技术人员？ → Coze（唯一真零代码）
```

### PM 视角评价

- **n8n**：护城河是 400+ 连接器。但传统产品加 AI 壳，如果 Agent 成主流可能被取代
- **Coze**：最大优势是字节生态 + 零门槛，但"上限低"——简单好做、复杂做不了
- **Dify**：壁垒是开源 + LLMOps 全链路。最接近你们的 RAG 评测体系设计思路。风险是：大模型能力进化到"不需精细调教"时，Dify 的复杂度反成劣势

**面试金句**：
> "n8n 是自动化老兵学 AI，Coze 是让所有人玩 AI，Dify 是让开发者造 AI。一个从过去走向未来，一个从未来走向大众，一个让未来可编程。"

## Q13: 自建 RAG vs 用 Dify/Coze，怎么决策？迁移要怎么做？

> **一句话**：先用 Dify 搭原型验证可行性。如果 80% 需求在平台天花板之下，就用平台。撞到天花板了，再自建核心模块。最佳实践：平台做底座 + 自建做差异化。

### 自建 vs 平台优劣对比

| 维度 | 自建 | Dify | Coze |
|------|------|------|------|
| 分块策略 | ⭐⭐⭐⭐⭐ 4策略自适应 | ⭐⭐⭐ 通用分块 | ⭐⭐ 黑盒 |
| 检索可控 | ⭐⭐⭐⭐⭐ 代码级 | ⭐⭐⭐⭐ 配置级 | ⭐⭐ 有限配置 |
| 评测能力 | ⭐⭐⭐⭐⭐ TREC 框架 | ⭐⭐⭐ 日志+标注 | ⭐ 几乎无 |
| 重排 | ❌ 待开发 | ✅ 开箱即用 | ❌ 无 |
| 多模型 | ⭐⭐ 手动 | ⭐⭐⭐⭐⭐ 100+ | ⭐⭐⭐⭐ |
| 数据安全 | ⭐⭐⭐⭐⭐ 内网 | ⭐⭐⭐⭐ 可私有部署 | ⭐⭐ Cloud Only |
| 业务集成 | ⭐⭐⭐⭐⭐ TB数据+权限 | ⭐⭐⭐ API集成 | ⭐⭐ 插件开发 |
| 开发成本 | 🔴 高 | 🟡 中 | 🟢 低 |
| 定制天花板 | ⭐⭐⭐⭐⭐ 无限 | ⭐⭐⭐ 受平台限制 | ⭐ 严重受限 |

核心 trade-off：
```
自建：控制力 ↑↑↑  开发成本 ↑↑↑  天花板 ↑↑↑
Dify：控制力 ↑↑   开发成本 ↑    天花板 ↑↑
Coze：控制力 ↑     开发成本 ↓    天花板 ↓
```

### 自建系统不能被平台替代的三个优势

| 能力 | 自建能做到 | 平台做不到 |
|------|-----------|-----------|
| 钉钉文档自动增量同步 | 定时拉取→解析→分块→嵌入，全自动 | 需手动上传或自建同步脚本 |
| TREC Pooling 评测 | 三路检索合并→LLM 标注→人工复核 | 平台无 Pooling |
| TB 任务数据融合 | 知识库 + TB 任务 → LLM 综合 | 需额外开发 |

### 迁移到 Dify 怎么做（约 1 周）

```
步骤1：数据迁移（1-2天）→ 导出 SQLite chunk → Dify API 批量导入
步骤2：配置 RAG（半天）→ 选嵌入模型、配分块参数、开混合检索+Rerank
步骤3：接入 LLM（半天）→ 配 one-api 或 DeepSeek 直连
步骤4：集成（1-2天）→ Dify API 替代 chat.py
步骤5：评测验证（1天）→ 用现有 26 道题跑一遍对比指标
```

### PM 做技术决策的三个问题

```
Q1: 标准需求还是差异化需求？
    标准 → 平台    差异 → 自建

Q2: 快速验证还是长期迭代？
    快速 → 平台    长期 → 自建

Q3: 团队有工程资源吗？
    有 → 自建核心模块 + 平台辅助    没有 → 平台为主 + 最小自建
```

**面试回答模板**：
> 我评估过 Dify，它能覆盖 80% 的 RAG 需求。但我们有三个能力是平台做不到的：钉钉文档自动增量同步、TREC 标准评测体系、TB 任务数据融合。如果重来一次，我会用 Dify 做 RAG 底座，省掉基础设施开发，但保留自建的评测体系、数据同步和业务集成层。平台做底座 + 自建做差异化 = ROI 最高。
