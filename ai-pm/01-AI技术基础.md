## Q1: AI Agent 的本质是什么？Harness 是什么？

> **一句话**：AI Agent = LLM + 工具 + 自主决策循环。Harness 是 Agent 的"操作系统"——在你们的系统中就是 ttyd 终端 + Claude CLI + Skills 工作区。

### Agent 的本质

传统 LLM 调用是"一问一答"：用户输入 → 模型输出 → 结束。

Agent 的模式是"自主多步执行"：

```
用户给目标 → Agent 自主规划步骤
  → 步骤1: 调用工具A（比如搜索知识库）
  → 步骤2: 分析结果，发现不够，换策略再搜
  → 步骤3: 调用工具B（比如创建任务）
  → 步骤4: 综合所有信息，输出最终结果
```

**核心区别**：普通 LLM 是被动回答，Agent 是主动规划和执行。

### Agent 的三要素

| 要素 | 说明 | 你们的实现 |
|------|------|-----------|
| **规划能力** | 分解目标为步骤 | SKILL.md 定义的流程 + Claude CLI 自主决策 |
| **工具调用** | 操作外部系统 | curl（知识库检索）、文件读写（draft.json）、钉钉 API |
| **记忆/上下文** | 记住历史交互 | 工作区文件（AI_TASK_CONTEXT.md）、会话历史 |

### Harness = Agent 的执行环境

Harness 给 AI 一个"操作系统"。在你们的系统中，具体形态是 **ttyd 终端 + Claude CLI + Skills 工作区**：

```
用户通过 Web 界面打开 AI 终端
  → ttyd 提供浏览器内的终端会话
  → Claude CLI 作为 Agent 运行在终端中
  → Skills 目录下的 SKILL.md 定义 Agent 的行为规则
  → Agent 可以执行 curl（查知识库）、读写文件（draft.json）、调用 API
```

以 TB 任务创建为例，Agent 的执行流程：
1. 读取 AI_TASK_CONTEXT.md 了解用户上下文
2. 一问一答收集：标题 → 工时类型 → 背景 → 产出 → 时间
3. 自动生成规范化的需求描述和产出清单
4. 写入 draft.json
5. 用户确认后，后端调用钉钉 API 创建真实任务

**面试回答模板**：
> Agent 的本质是"LLM + 工具 + 自主决策循环"。我们的 TB 任务创建就是一个典型 Agent——它不是简单问答，而是引导式多步交互：收集标题、工时、背景，自动生成规范描述，确认后调用钉钉 API 创建真实任务。整个过程是 Agent 自主规划和执行的。

## Q2: RAG 是什么？有哪些替代方案？各有什么优劣？

> **一句话**：RAG（检索增强生成）= 先检索相关文档片段，再让 LLM 基于片段生成回答。它的核心 trade-off 是"用检索换记忆"——检索可能漏，但知识更新快、可溯源。

### 替代方案全景对比

| 方法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **RAG** | 检索文档片段 → LLM 生成 | 知识更新快、可溯源、成本低 | 检索质量不可控、可能漏召回 |
| **Fine-tuning（微调）** | 用企业文档训练专属模型 | 知识内化，不需要检索 | 更新需重新训练、成本高、无法溯源 |
| **Prompt Engineering** | 把所有知识写在 system prompt 里 | 简单直接 | 上下文窗口有限，知识量大时不可行 |
| **纯关键词搜索 + LLM** | FTS 检索 + LLM 生成 | 简单 | 语义理解弱，同义词匹配不了 |
| **Graph RAG** | 用知识图谱替代向量检索 | 实体关系推理强 | 构建成本高，维护复杂 |
| **Agentic RAG** | Agent 多步检索，自主判断充分性 | 检索质量更高 | 延迟增加，多次 LLM 调用 |

### RAG 的 7 个常见问题（诚实面对）

| 问题 | 说明 | 你们的处理 |
|------|------|---------|
| 检索质量不可控 | 召回不全或不准 | 对照试验量化，TREC 标准评测 |
| 分块策略影响大 | 切太碎丢上下文，切太大精度降 | 4 策略自适应分块 |
| LLM 忽略检索结果 | 模型"自作主张" | System prompt 约束 + 来源引用 |
| 无法回答推理问题 | RAG 是"找答案"不是"推理" | 复杂问题用 Agent 多步检索 |
| 知识更新延迟 | 文档更新 → 分块 → 嵌入有延迟 | 手动触发同步，后续做增量更新 |
| 上下文窗口浪费 | 检索 20 条，可能 5 条有用 | 加 reranker 精排 |
| 同义词/术语不匹配 | 用户说的和文档写的不一样 | Embedding 语义检索弥补 |

### RAG vs Fine-tuning 决策框架

```
知识频繁更新？ → 是 → RAG
                → 否 → 考虑 Fine-tuning

需要溯源引用？ → 是 → RAG
                → 否 → Fine-tuning 可以

数据量大（远超上下文）？ → 是 → RAG
                        → 否 → Prompt 直接塞

需要推理能力？ → 是 → 二者结合（RAG 检索 + Fine-tuned 模型推理）
```

**面试金句**：
> "RAG 不是银弹。它的核心 trade-off 是用检索换记忆——检索可能漏，但知识更新快、可溯源。Fine-tuning 是用训练换记忆——知识内化更准确，但更新成本高。没有最好，只有最合适的场景。"

## Q3: AI 大模型和传统工程化的边界在哪里？怎么判断该不该用 AI？

> **一句话**：先用工程方法解决 80% 的确定性问题，再用 AI 解决 20% 的模糊问题。反过来——先上 AI 再补工程——会导致不可控的质量问题。

### 核心判断框架

| 维度 | 适合工程化 | 适合 AI |
|------|-----------|---------|
| **输入是否确定** | 确定的（if-else 能穷举） | 开放式的（自然语言、图像） |
| **规则是否明确** | 明确的（业务规则、计算公式） | 模糊的（需要理解语义） |
| **是否需要创造性** | 不需要（标准化流程） | 需要（内容生成、推理） |
| **容错要求** | 零容错（金融交易） | 可容错（搜索、推荐） |
| **数据特征** | 结构化、标签化 | 非结构化、多模态 |
| **更新频率** | 低频（业务规则稳定） | 高频（知识持续变化） |

### 具体场景判断

| 场景 | 用 AI？ | 理由 |
|------|---------|------|
| 计算员工工时 | ❌ 工程化 | 规则明确、零容错 |
| 理解文档内容回答问题 | ✅ AI | 非结构化、开放式查询 |
| 审批流程流转 | ❌ 工程化 | 规则确定，不需要"理解" |
| 自动生成周报摘要 | ✅ AI | 需要理解+生成，容错较高 |
| 数据库 CRUD | ❌ 工程化 | 确定性高，AI 反而可能出错 |
| 语义搜索 | ✅ AI | 同义词、口语化，规则穷举不了 |
| 图像质检（合格/不合格） | ⚠️ 看情况 | 规则明确→传统 CV；模糊标准→AI |

> 具体工程/AI 边界划分案例见 [02-RAG系统设计 Q7](./02-RAG系统设计.md#q7-你们的-rag-系统是怎么设计的为什么自建而不是用钉钉-ai)

### 实用判断公式

```
适合用 AI = 
  输入不确定（自然语言/图像/音频）
  × 输出不需要 100% 精确
  × 人工做成本高/速度慢
  × 有足够的测试数据验证效果

四个全满足 → 用 AI
一个不满足 → 慎重
两个不满足 → 大概率不该用
```

**面试金句**：
> "先用工程方法解决 80% 的确定性问题，再用 AI 解决剩余 20% 的模糊问题。反过来——先上 AI 再补工程——往往会导致不可控的质量问题。"

## Q4: 大模型的"幻觉"是什么？怎么理解和缓解？

> **一句话**：幻觉 = 模型生成了看似合理但实际不存在的内容。RAG 系统的幻觉根因是检索质量——检索不到的，模型就会"编"。缓解靠三层：检索提质量、生成做验证、呈现加置信度。

### 幻觉在 RAG 系统中的三种表现

| 类型 | 表现 | 根因 |
|------|------|------|
| 检索失败型 | 没有召回相关内容 → 模型"编造" | 检索质量不足 |
| 过度推理型 | 检索到部分内容 → 模型补充了文档中没有的细节 | LLM 的生成惯性 |
| 错误关联型 | 跨文档综合 → 模型错误关联不相关信息 | 检索片段之间缺乏关系建模 |

### 你们当前的缓解措施

- System prompt 明确要求："资料不足时明确告知，不编造"
- 检索结果附带来源引用，用户可追溯验证
- Temperature 设为 0.3（降低随机性，但无法消除幻觉）

### 更完善的幻觉防控体系

```
层级1 — 检索侧（源头防）
  检索后评估：用 Self-RAG 思路，检索完先判断是否充分
  不够 → 重新检索，不强行生成
  
层级2 — 生成侧（过程控）
  答案验证：生成后，用另一个 prompt 验证是否与检索内容一致
  不一致 → 回退，标注"信息不足"
  
层级3 — 呈现侧（用户知）
  置信度标注：对低置信度回答标注"仅供参考"
  引用精确到 chunk：不是引用整个文档，而是具体段落
```

### 如何判断"是不是为了 AI 而 AI"

三个自检问题：

| 问题 | 判定 |
|------|------|
| 这个问题不用 AI 能不能解决？ | 能 → AI 可能是多余的 |
| AI 方案比非 AI 方案在哪个维度更好？ | 说不清 → 为 AI 而 AI |
| AI 的隐性成本（幻觉、延迟、维护）是否被接受了？ | 没想过 → 不够诚实 |

防"锤子思维"的 PM 方法：
1. 先定义问题，再选工具。不是先选了 AI 再找场景
2. 每个 AI 功能配套"不用 AI 的降级方案"
3. 用指标说话——AI 版不比非 AI 版好，就不上

**面试金句**：
> "幻觉的根因不是模型'爱撒谎'，而是检索质量不够。检索不到的，模型就会补。所以我们的核心工作是提升检索质量——用 TREC 标准评测、做对照试验，从源头减少幻觉。"

## Q5: 精度和召回率在 RAG 系统里怎么理解和平衡？

> **一句话**：召回率 = "该找的都找到了吗"，精度 = "找到的都是有用的吗"。RAG 优化策略是——先多召回保召回率，再用 reranker 精排提精度。

### 概念速查

| 概念 | 含义 | 极端表现 |
|------|------|---------|
| **精度（Precision）** | 检索到的内容中，有多少是相关的 | 精度高 = 每条都有用，但可能漏 |
| **召回率（Recall）** | 所有相关内容中，检索到了多少 | 召回高 = 基本不漏，但噪声多 |
| **MRR** | 第一个相关结果排第几 | 衡量排名质量 |
| **nDCG** | 综合相关性和排名位置 | 更全面的排名指标 |

> 具体系统的精度-召回优化策略见 [02-RAG系统设计 Q7](./02-RAG系统设计.md#q7-你们的-rag-系统是怎么设计的为什么自建而不是用钉钉-ai)

### Precision @ K vs Recall @ K 的应用场景

| 场景 | 侧重 | 原因 |
|------|------|------|
| 客服知识库 | 精度优先 | 答错比不答更糟 |
| 法律文书检索 | 召回优先 | 漏掉关键判例是灾难 |
| 企业内部问答 | 平衡 | 既要准（别浪费用户时间），又要全（别漏关键信息） |

**面试回答模板**：
> "我们在 RAG 优化中同时监控 Recall@5、MRR 和 nDCG。策略上采用'先多召回再精排'——用 bge-small 做粗召回保召回率，用 reranker 做精排提精度。这比简单调 top_k 更有效，因为它在两个维度上独立优化。"

## Q6: AI 行业有哪些关键发展节点？

> **一句话**：从 2017 年 Transformer 架构奠定基础，到 2022 年 ChatGPT 引爆，再到 2025-2026 年 Agent 从实验走向生产——AI 行业经历了"架构突破 → 规模验证 → 产品爆发 → Agent 落地"四个阶段。

### 大模型关键时间线

| 时间 | 事件 | 意义 |
|------|------|------|
| 2017.06 | Google 发布 Transformer 论文 | 奠定现代 LLM 架构基础 |
| 2020.05 | OpenAI 发布 GPT-3 (175B) | 展示大模型 emergent ability |
| 2021.06 | GitHub Copilot 发布（基于 Codex） | AI 编码助手进入主流 |
| 2022.11 | **ChatGPT 发布** | 🔥 引爆全球 AI 浪潮 |
| 2023.03 | GPT-4 + Claude 发布 | 多模态、推理、安全对齐 |
| 2023.06 | Agent 概念爆发（AutoGPT, BabyAGI） | Agent 范式进入公众视野 |
| 2024-2025 | DeepSeek-V3、Qwen、GLM 等国产模型崛起 | 中文能力 + 成本优势 |
| 2025-2026 | MCP 协议、AI IDE（Cursor/Windsurf）成熟 | Agent 从实验走向生产 |

### Agent 概念演进

Agent 不是新概念——1980 年代就在研究。关键是 **2023 年是 LLM-based Agent 的爆发点**：

- 2023.03：AutoGPT 发布，展示 LLM 自主分解目标执行多步任务
- 2023.04：BabyAGI、AgentGPT 涌现
- 2023.06：LangChain Agent 模块成熟
- 2024-2025：Agent 从玩具走向生产（客服 Agent、编码 Agent、数据分析 Agent）

### Claude 和 Codex 的关键时间点

- **Codex**：2021.08 发布，2021.10 GitHub Copilot 上线——AI 编码助手的开端
- **Claude**：2023.03 发布，2023.07 Claude 2 支持 100K 上下文
- **Claude Code**：2025 年推出，Agent 能力直接嵌入开发环境

### 已验证的落地场景

| 场景 | 案例 | 成熟度 |
|------|------|--------|
| 编码助手 | GitHub Copilot, Cursor | ⭐⭐⭐⭐⭐ |
| 客服机器人 | 电商/金融客服 | ⭐⭐⭐⭐ |
| 知识库问答 | 企业 RAG | ⭐⭐⭐⭐ |
| 文档生成 | 合同/报告自动生成 | ⭐⭐⭐ |
| 数据分析 | 自然语言查数据库 | ⭐⭐⭐ |
| Agent 自动化 | 流程自动化 | ⭐⭐ |
