> 10 个 AI 产品经理面试必问的底层问题。不是背答案，是理解本质。

## 一、什么是 AI Agent？Harness 是什么？

### 1.1 AI Agent 的本质

AI Agent = **LLM + 工具 + 自主决策循环**。

传统 LLM 调用是"一问一答"：用户输入 → 模型输出 → 结束。

Agent 的模式是"自主多步执行"：

```
用户给目标 → Agent 自主规划步骤
  → 步骤1: 调用工具A（比如搜索知识库）
  → 步骤2: 分析结果，发现不够，换策略再搜
  → 步骤3: 调用工具B（比如创建任务）
  → 步骤4: 综合所有信息，输出最终结果
```

**核心区别**：普通 LLM 是被动回答，Agent 是主动规划和执行。

### 1.2 Harness（AI 工作台）

Harness 是 **Agent 的执行环境**——给 AI 一个"操作系统"。

在我们的系统中，Harness 的具体形态是 **ttyd 终端 + Claude CLI + Skills 工作区**：

```
用户通过 Web 界面打开 AI 终端
  → ttyd 提供浏览器内的终端会话
  → Claude CLI 作为 Agent 运行在终端中
  → Skills 目录下的 SKILL.md 定义 Agent 的行为规则
  → Agent 可以执行 curl（查知识库）、读写文件（draft.json）、调用 API
```

我们的 Skills 系统包含 7 个技能：
- `0_server_ops` — 服务器运维
- `1-1_keyword_extract` — 关键词提取
- `1_tb_analysis` — TB 数据分析
- `2_perf_analysis` — 绩效分析
- `2_tb_create` — TB 任务创建（多步骤引导式 Agent）
- `3_kb_qa` — 知识库问答

以 TB 任务创建为例，Agent 的执行流程：

```
1. 读取 AI_TASK_CONTEXT.md 了解用户上下文
2. 一问一答收集：标题 → 工时类型 → 背景 → 产出 → 时间
3. 自动生成规范化的需求描述和产出清单
4. 写入 draft.json
5. 用户确认后，后端调用钉钉 API 创建真实任务
```

这就是 **Agent 的实际应用**——不是聊天机器人，而是能操作真实业务系统的自主执行体。

### 1.3 Agent 的三要素

| 要素 | 说明 | 我们的实现 |
|------|------|-----------|
| **规划能力** | 分解目标为步骤 | SKILL.md 定义的流程 + Claude CLI 自主决策 |
| **工具调用** | 操作外部系统 | curl（知识库检索）、文件读写（draft.json）、钉钉 API |
| **记忆/上下文** | 记住历史交互 | 工作区文件（AI_TASK_CONTEXT.md）、会话历史 |

## 二、模型怎么调用的？是否泄露内部资料和代码？

### 2.1 当前调用方式

```
用户请求 → Flask 后端
  → 检索本地知识库（MySQL + pgvector）
  → 拼接 prompt（system prompt + 检索到的文档片段 + 用户问题）
  → HTTP POST → one-api 代理（one-api.server22.jz）
  → 转发到模型服务商（DeepSeek）
  → 流式返回 SSE
```

关键参数：
- 模型：`deepseek-v4-flash`
- Temperature：0.3（有一定的确定性）
- Max tokens：4096
- 通过 one-api 统一代理，API key 统一管理

### 2.2 数据安全分析

| 环节 | 数据暴露 | 风险等级 |
|------|---------|---------|
| 知识库文档内容 | 作为 prompt 发送给 LLM | ⚠️ 中 |
| 源代码 | **不发送**。只发送知识库文档 | ✅ 低 |
| TB 任务数据 | 检索到的任务标题/状态 | ⚠️ 中 |
| 用户身份 | 不发送给 LLM | ✅ 低 |
| API Key | 存储在 config.json（明文） | 🔴 高 |

**实际情况**：
- 文档内容确实会离开内网（经过 one-api 代理转发到 DeepSeek 等模型服务商）
- 但 one-api 是内部部署的代理层，可以在网关层做审计和限流
- 不会发送源代码，只发送知识库的 markdown 文档片段
- API key 明文存储是安全隐患，生产环境应该用环境变量或密钥管理服务

### 2.3 改进方向

```
当前：文档内容 → one-api 代理 → 外部模型服务商
改进1：one-api 内部部署开源模型（如 DeepSeek 私有化部署），数据不出内网
改进2：敏感文档做脱敏/摘要后再发送
改进3：按知识库分级——机密文档走本地模型，普通文档走云端
```

### 2.4 面试回答模板

> 我们通过 one-api 内部代理统一管理模型调用，文档内容会在检索后作为 prompt 发送给模型。目前风险可控——不发送源代码，只发送知识库 markdown 文档。如果对安全要求更高，可以在 one-api 后面挂私有化部署的开源模型，数据完全不出内网。这是一个可以逐步加固的过程，当前阶段优先解决"能不能用"的问题。

## 三、如果不用 RAG，有什么其他方法？RAG 存在什么问题？

### 3.1 替代方案对比

| 方法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **Fine-tuning（微调）** | 用企业文档训练专属模型 | 知识内化到模型参数，不需要检索 | 知识更新需重新训练；成本高；无法溯源 |
| **Prompt Engineering** | 把所有知识写在 system prompt 里 | 简单直接 | 上下文窗口有限，知识量大时不可行 |
| **纯关键词搜索 + LLM** | FTS 检索 + LLM 生成 | 简单 | 语义理解弱 |
| **Graph RAG** | 用知识图谱替代向量检索 | 实体关系推理强 | 构建成本高 |
| **Agentic RAG** | Agent 多步检索，自主判断充分性 | 检索质量更高 | 延迟增加，多次 LLM 调用 |

### 3.2 RAG 的问题（诚实面对）

| 问题 | 说明 | 当前状态 |
|------|------|---------|
| **检索质量不可控** | 召回不全或不准，直接影响回答质量 | 正在通过对照试验量化 |
| **分块策略影响大** | 切得太碎丢上下文，切得太大检索精度下降 | 4 策略自适应，已较好 |
| **LLM 可能忽略检索结果** | 模型有时"自作主张"，不只用检索内容 | system prompt 约束 |
| **无法回答需要推理的问题** | RAG 是"找答案"，不是"推理答案" | 复杂跨文档问题召回不足 |
| **知识更新延迟** | 文档更新 → 重新分块 → 重新嵌入，有延迟 | 手动触发同步 |
| **上下文窗口浪费** | 检索 20 条，可能只有 5 条有用 | 缺重排导致浪费 |
| **同义词/术语不匹配** | 用户说的和文档写的不一样 | embedding 部分解决 |

### 3.3 RAG vs Fine-tuning 的决策框架

```
知识频繁更新？ → 是 → RAG
                → 否 → 考虑 Fine-tuning

需要溯源引用？ → 是 → RAG
                → 否 → Fine-tuning 可以

数据量巨大（远超上下文窗口）？ → 是 → RAG
                              → 否 → Prompt 直接塞

需要推理能力？ → 是 → 二者结合（RAG 检索 + Fine-tuned 模型推理）
```

### 3.4 面试金句

> "RAG 不是银弹。它的核心 trade-off 是用检索换记忆——检索可能漏，但知识更新快、可溯源。Fine-tuning 是用训练换记忆——知识内化更准确，但更新成本高。没有最好，只有最合适的场景。"

## 四、模型的幻觉？失准？精度、召回率怎么处理？会不会为了 AI 而 AI？

### 4.1 幻觉（Hallucination）

**定义**：模型生成了看似合理但实际不存在的、或与事实不符的内容。

**在我们的系统中的表现**：
- 检索没有召回相关内容 → 模型"编造"答案
- 检索到部分相关内容 → 模型过度推理，补充了文档中没有的细节
- 跨文档综合 → 模型错误关联不相关的片段

**当前缓解措施**：
- System prompt 明确要求："资料不足时明确告知，不编造"
- 检索结果附带来源引用，用户可追溯验证
- Temperature 设为 0.3（降低随机性，但无法消除幻觉）

**更完善的方案**：
```
1. 检索后评估（Self-RAG）：检索完先判断是否充分，不够就重新检索
2. 答案验证：生成答案后，用另一个 prompt 验证是否与检索内容一致
3. 置信度标注：对低置信度回答标注"仅供参考"
4. 引用精确到段落：不是引用整个文档，而是具体 chunk
```

### 4.2 精度 vs 召回率

这是信息检索的经典 trade-off：

| 概念 | 含义 | 极端表现 |
|------|------|---------|
| **精度（Precision）** | 检索到的内容中，有多少是相关的 | 精度高 = 每条都有用，但可能漏掉 |
| **召回率（Recall）** | 所有相关内容中，检索到了多少 | 召回高 = 基本不漏，但混入很多噪音 |
| **F1 分数** | 精度和召回率的调和平均 | 综合平衡指标 |

**在我们的 RAG 优化中**：
- 当前检索 top-20 → 融合 → 取 top-8。这是在**保精度**（宁可少，不要错）
- 对照试验用 Recall@5 评估，是在**测召回能力**
- 加 reranker 是在**不牺牲召回的提精度**——先多召回（保召回），再精排去噪（提精度）

### 4.3 会不会为了 AI 而 AI？拿着锤子找钉子？

**这是个好问题，PM 必须诚实回答。**

检验标准——问自己三个问题：

| 问题 | 自检 |
|------|------|
| 这个问题不用 AI 能不能解决？ | 能 → AI 可能是多余的 |
| AI 方案比非 AI 方案在哪个维度更好？ | 说不清 → 为 AI 而 AI |
| AI 的隐性成本（幻觉、延迟、维护）是否被接受了？ | 没想过 → 不够诚实 |

**我们在做的**：
- 内部知识库问答 → AI 是合理的（非结构化数据、开放式查询、工程方案不可行）
- TB 任务创建 → AI 有争议（可以纯表单，但 AI 能自动提取需求、生成规范化描述，确实提升体验）

**防"锤子思维"的方法**：
1. 先定义问题，再选工具。不是先选了 AI 再找场景
2. 每个 AI 功能配套"不用 AI 的降级方案"
3. 用指标说话——如果 AI 版不比非 AI 版好，就不上

## 五、用户真的会使用吗？如果不用我们的工具应该用什么？

### 5.1 用户使用意愿的现实

企业内部工具的宿命：**做了不一定有人用。**

原因：
- 用户习惯已形成（直接问同事、翻钉钉文档）
- 对 AI 回答的信任度不够（担心编造）
- 使用门槛（需要打开特定页面、学习怎么提问）
- 答案不够好 → 用一次就放弃

### 5.2 如果不用我们的 AI 工具，用户现在用什么？

| 场景 | 当前做法 | AI 工具的替代价值 |
|------|---------|------------------|
| 查技术文档 | 在钉钉里搜索，逐篇翻 | 语义搜索 + 直接给答案 |
| 了解项目进度 | 问同事 / 翻 TB | AI 自动汇总 |
| 新人学习 | 问老员工 | 自助问答，减轻老员工负担 |
| 跨部门信息 | 拉群问 / 开会 | 一站式查询 |
| 创建任务 | 手动填表单 | AI 引导 + 自动生成 |

**关键认知**：AI 工具不是替代"什么都不做"，而是替代"低效的做法"。只要比当前做法好一个数量级（更快、更准、更方便），就有价值。

### 5.3 怎么让用户真的用？

```
1. 嵌入工作流：不要另开页面，集成到钉钉机器人、IDE 插件
2. 解决真痛点：不是"什么都能问"，而是聚焦 3 个高频场景做到极致
3. 信任建设：展示引用来源、支持反馈"答得不对"
4. 冷启动：找 2-3 个种子用户，优化到他们满意后再推广
5. 效果可见：对比"查文档 10 分钟 vs AI 30 秒"，让价值可感知
```

## 六、只有内部提效作用吗？有没有商业化用途？

### 6.1 三层价值递进

```
第一层：内部提效（已实现）
  研发团队内部使用，提升文档检索和问题解答效率

第二层：产品化（可探索）
  打包成 SaaS 产品卖给其他有类似需求的公司
  例如：制造业企业的技术文档知识库

第三层：行业解决方案（远期）
  针对特定行业（机器人/智能制造）定制，含行业知识图谱
```

### 6.2 商业化路径分析

| 路径 | 目标客户 | 价值主张 | 可行性 |
|------|---------|---------|--------|
| **企业知识库 SaaS** | 有大量内部文档的中型企业 | 开箱即用的 RAG 知识库 | ⭐⭐⭐ 技术成熟，市场有需求 |
| **现场运维知识助手** | 设备制造商的售后团队 | 现场工程师手机查维修方案 | ⭐⭐⭐ AGV/机器人行业刚需 |
| **行业专用 AI** | 智能制造/物流行业 | 行业术语理解 + 行业文档模板 | ⭐⭐ 需要行业数据积累 |
| **钉钉应用市场插件** | 钉钉生态企业 | 在钉钉内直接使用，无需切换 | ⭐⭐⭐ 渠道优势 |

### 6.3 核心判断

> "内部提效是商业化的 MVP。先在内部把体验和效果打磨到极致，证明 RAG 在真实文档环境下的价值，再考虑对外输出。但思路不能局限——这套能力本质上是'非结构化企业知识的 AI 化'，适用场景远不止一家公司。"

## 七、模型上下文超过了怎么办？现在有处理吗？

### 7.1 上下文窗口是什么

每个 LLM 有最大输入 token 数限制。超过限制，模型会截断或拒绝。

当前配置：
- `_MAX_CONTEXT_TOKENS = 8000`
- 从检索结果中逐条累加，token 总数超过 8000 就停止添加

### 7.2 当前处理方式

```python
# chat.py 中的处理逻辑
total_tokens = 0
for r in results:
    tk = r.get("token_count") or len(content) // 2
    if total_tokens + tk > _MAX_CONTEXT_TOKENS:
        break  # 超过限制，后面的 chunk 直接丢弃
    parts.append(content)
    total_tokens += tk
```

**当前做法**：简单截断。检索结果按 RRF 排序，token 不够就丢弃排后面的。

**问题**：
- 后面的 chunk 直接丢弃，可能丢失重要信息
- 没有做任何压缩、摘要或重排优化
- 8000 token 对于 deepseek-v4 来说过于保守（该模型支持更大的上下文）

### 7.3 更优的处理策略

| 策略 | 说明 | 优缺点 |
|------|------|--------|
| **Summary 压缩** | 用 LLM 先对每个 chunk 做摘要，再拼接 | 保留信息但多一次 LLM 调用 |
| **Rerank 精排** | 先粗召回 20 条，用 reranker 精排到 8 条 | 保证进 prompt 的都是最相关的 |
| **动态窗口** | 根据模型实际能力动态调整上限 | 利用大窗口，减少截断 |
| **分层检索** | 先搜章节摘要，命中后再加载完整内容 | 类似"目录 → 正文"的阅读方式 |
| **Map-Reduce** | 分批生成部分回答，再合并 | 适合超长文档的问答 |

### 7.4 我们的改进空间

当前对照试验中计划加入 reranker（Group B/D/E），这本身就是对上下文利用率的优化——从 20 条中精挑 8 条，比简单截断有效得多。

## 八、响应速度？

### 8.1 当前延迟构成

```
用户提问 → 检索（~200-500ms）→ prompt 拼接（<10ms）→ LLM 生成（2-10s）
```

| 环节 | 耗时 | 优化空间 |
|------|------|---------|
| SQLite FTS 关键词检索 | ~10-50ms | 很小 |
| pgvector 向量检索 | ~100-300ms | 加索引、升级硬件 |
| RRF 融合 | ~5ms | 很小 |
| LLM 首 token | ~500-2000ms | 换更快模型、流式输出已做 |
| LLM 完整生成 | 2-10s | 流式输出已做，用户可边看边等 |

### 8.2 已做的优化

- 流式输出（SSE）：用户不用等全部生成完，首 token 出现即可开始阅读
- 状态提示："检索本地向量知识库" → "调用模型生成回答"，让等待可感知

### 8.3 可以做的优化

| 优化 | 预期效果 | 成本 |
|------|---------|------|
| 检索结果缓存 | 相同/相似 query 秒回 | 需要相似度判断 + 缓存策略 |
| 换更快的模型 | deepseek-v4-flash 已经较快 | - |
| 预加载 embedding 模型 | 减少首次检索延迟 | 内存占用 |
| 减少检索 top_k | 从 20 降到 10-15 | 可能影响召回 |

### 8.4 面试话术

> "当前端到端延迟在 2-10 秒，通过 SSE 流式输出让用户可以边等边看。检索约 200-500ms，主要耗时在 LLM 生成。后续计划加入检索缓存——相同 query 不需要重复检索和生成，秒级返回。"

### 9.2 Agent 概念的演进

Agent 不是新概念——AI 领域从 1980 年代就在研究智能体。但 **2023 年 3-6 月是"LLM-based Agent"的爆发点**：

- 2023.03：AutoGPT 发布，展示 LLM 自主分解目标、执行多步骤任务

- 2024-2025：Agent 从玩具走向生产（客服 Agent、编码 Agent、数据分析 Agent）

### 9.3 Claude 和 Codex 的时间线

- **Codex**：2021.08 发布（OpenAI），2021.10 GitHub Copilot 上线。这是 AI 编码助手的开端
- **Claude**：2023.03 发布（Anthropic），以安全对齐和长上下文见长。2023.07 Claude 2 支持 100K 上下文
- **Claude Code**：2025 年推出，将 Agent 能力直接嵌入开发环境

### 9.4 AI 产品经理的前景

**现状**：AI PM 是目前最紧缺的产品岗位之一，原因很简单——大多数 PM 懂产品但不懂 AI，少数懂 AI 的又不懂产品。

**AI PM 的核心能力变化**：

| 传统 PM | AI PM |
|---------|-------|
| 写 PRD | 写 prompt 和评估标准 |
| 画原型 | 定义 Agent 行为流程 |
| 用户调研 | 构建评测数据集 |
| 竞品分析 | 模型选型评估 |
| 数据分析 | 模型的精度/召回/延迟分析 |

**AI PM 的三个方向**：

1. **AI Native 产品 PM**：做以 AI 为核心价值的产品（如 ChatGPT、Copilot）
2. **AI 平台/工具 PM**：做 AI 开发平台（如 Dify、Coze、LangChain）
3. **AI 赋能传统产品 PM**：在现有产品中集成 AI 能力（如我们现在做的）

**3-5 年趋势判断**：
- AI PM 会从"特殊岗位"变成"基础能力"——就像现在 PM 都需要懂数据分析
- 真正稀缺的是**能定义 AI 产品的评估标准、能设计 Agent 工作流、能做模型选型 trade-off** 的 PM
- 最危险的 PM 是"只会调用 API 的 AI PM"——门槛太低，没有壁垒

### 9.5 现有的落地场景和实际意义

**已验证的落地场景**：

| 场景 | 案例 | 成熟度 |
|------|------|--------|
| 编码助手 | GitHub Copilot, Cursor | ⭐⭐⭐⭐⭐ |
| 客服机器人 | 电商/金融客服 | ⭐⭐⭐⭐ |
| 知识库问答 | 企业 RAG | ⭐⭐⭐⭐ |
| 文档生成 | 合同/报告自动生成 | ⭐⭐⭐ |
| 数据分析 | 自然语言查数据库 | ⭐⭐⭐ |
| Agent 自动化 | 订票/填表/流程自动化 | ⭐⭐ |

**实际意义**：
- AI 不是万能的，但在"信息检索 + 内容生成"领域的效率提升是真实的
- 企业场景下，AI 的 ROI 最容易量化——节省了多少人工时间
- 但 AI 的成本（token 费用、延迟、幻觉风险）也需要诚实计算

## 十、AI 大模型和工程化的边界在哪里？

### 10.1 核心判断框架

| 维度 | 适合工程化 | 适合 AI |
|------|-----------|---------|
| **输入是否确定** | 确定的（if-else 能穷举） | 开放式的（自然语言、图像） |
| **规则是否明确** | 明确的（业务规则、计算公式） | 模糊的（需要理解语义） |
| **是否需要创造性** | 不需要（标准化流程） | 需要（内容生成、推理） |
| **容错要求** | 零容错（金融交易） | 可容错（搜索、推荐） |
| **数据特征** | 结构化、标签化 | 非结构化、多模态 |
| **更新频率** | 低频（业务规则稳定） | 高频（知识持续变化） |

### 10.2 具体场景判断

| 场景 | 用 AI？ | 理由 |
|------|---------|------|
| 计算员工工时 | ❌ 工程化 | 规则明确（打卡时间-休息），零容错 |
| 理解文档内容回答提问 | ✅ AI | 非结构化、开放式查询 |
| 审批流程流转 | ❌ 工程化 | 规则确定，不需要"理解" |
| 自动生成周报摘要 | ✅ AI | 需要理解+生成，容错较高 |
| 数据库 CRUD | ❌ 工程化 | 确定性强，AI 反而可能出错 |
| 语义搜索 | ✅ AI | 同义词、口语化，规则穷举不了 |
| 图像分类（合格/不合格） | ⚠️ 看情况 | 规则明确时用传统 CV，样本多且标准模糊时用 AI |

### 10.3 我们的实践：AI 和工程化的结合

当前 RAG 系统的各个环节就是最好的例子：

```
✅ 工程化（确定性高）：
  - FTS 关键词检索 → 精确匹配，零幻觉
  - 文档同步管线 → 标准工程，不需要 AI
  - 4 策略分块 → 规则明确，不需要 AI
  - RRF 融合排序 → 经典算法，不需要 AI

✅ AI（需要理解和生成）：
  - 向量语义检索 → 理解同义词和语义
  - LLM 综合生成 → 多文档信息合成

⚡ 工程和 AI 协作的边界：
  - 检索阶段：工程粗筛（快）+ AI 精筛（准）
  - 生成阶段：AI 生成 + 工程约束（来源引用、格式规范）
```

### 10.4 决策原则

> "先用工程方法解决 80% 的确定性问题，再用 AI 解决剩余 20% 的模糊问题。反过来——先上 AI 再补工程——往往会导致不可控的质量问题。"

### 10.5 一个实用的判断公式

```
适合用 AI 的场景 = 
  输入不确定（自然语言/图像/音频）
  × 输出不需要 100% 精确（可容错）
  × 人工做成本高/速度慢
  × 有足够的测试数据验证效果
```

如果这四个条件都满足 → 用 AI

如果有一个不满足 → 慎重评估

如果有两个不满足 → 大概率不该用 AI

## 十一、多个 Skill 和 MCP 并存时，AI 选择会不会出问题？

> 这是 Agent 工程中最常见也最棘手的问题之一：当 AI 面前摆着多个工具/技能时，它怎么知道该用哪个？

### 11.1 我们当前的实际情况

系统同时存在两套 Agent 能力体系：

**体系 A：Skills（6 个 SKILL.md）**

```
skills/
├── 0_server_ops/SKILL.md        ← 服务器运维（SSH、查日志、重启服务）
├── 1-1_keyword_extract/SKILL.md ← 关键词提取
├── 1_tb_analysis/SKILL.md       ← TB 任务分析
├── 2_perf_analysis/SKILL.md     ← 绩效达标分析 + 排单建议
├── 2_tb_create/SKILL.md         ← TB 任务创建（引导式 Q&A）
└── 3_kb_qa/SKILL.md             ← 知识库问答
```

**体系 B：MCP Tools（4 个工具）**

```
tb-mcp MCP Server:
├── get_user_task_context    ← 获取用户任务上下文（列表、指标、父子关系）
├── create_teambition_task   ← 直接创建 Teambition 任务
├── search_knowledge_base    ← 语义搜索知识库
└── get_workhour_summary     ← 查询工时汇总
```

**执行环境**：Claude Code（通过 `~/.claude/mcp.json` 连接 tb-mcp），同时加载项目的 CLAUDE.md 和 SKILL.md 文件。

### 11.2 会不会出问题？—— 会的

**问题 1：功能重叠，AI 可能选错入口**

| 用户想做的事 | 可以走的路 | AI 可能选错 |
|-------------|-----------|------------|
| 创建任务 | SKILL.md 的 curl 方式 **vs** MCP 的 `create_teambition_task` | 可能走 curl，绕过了 MCP 的参数校验 |
| 搜知识库 | SKILL.md 的 curl 方式 **vs** MCP 的 `search_knowledge_base` | 可能走 curl，返回格式不一致 |
| 分析任务 | `1_tb_analysis` SKILL **vs** `2_perf_analysis` SKILL | 边界模糊，可能选错 skill |

**问题 2：Skill 描述模糊，触发条件重叠**

两个 TB 分析 skill 的边界不够清晰：
- `1_tb_analysis`："分析任务" → 什么算"分析"？
- `2_perf_analysis`："绩效达标分析" → 绩效分析也是分析任务
- 用户说"帮我看看我的任务情况"——两个都可能触发

**问题 3：MCP 工具和 Skill 的"双轨制"**

同一个能力有两个入口，AI 需要判断用哪个：
```
用户: "帮我创建一个导航相关的任务"
  → 路径A: 读 SKILL.md → curl 调 API → 返回 draft 确认 → 再 curl 创建
  → 路径B: 调 MCP get_user_task_context → MCP create_teambition_task
```

MCP 路径更直接（一步到位），但 AI 不一定选它——取决于 AI 先看到哪个。

**问题 4：Skill 数量膨胀后的认知负荷**

当前 6 个 skill + 4 个 MCP tool = 10 个可选能力。每增加一个，AI 的"选择困难"就增加一分。当 skill 数量达到 20+ 时，AI 选择错误的概率会显著上升。

### 11.3 为什么会出问题？

根本原因在于 **LLM 的"工具选择"本质上是语义匹配，而不是逻辑判断**：

```
用户输入 → LLM 理解意图 → 在所有 tool/skill 描述中做语义相似度匹配 → 选最相似的
```

问题在于：
1. **语义相似 ≠ 功能正确**。"分析任务"和"绩效分析"语义上高度相似，但功能完全不同
2. **描述质量决定选择质量**。Skill 描述写得不好，AI 就选不对
3. **没有"不知道选哪个就反问"的机制**。AI 通常会硬选一个，而不是说"我不确定"

### 11.4 解决方案

#### 方案 A：消除重叠（治本）

```
当前: SKILL.md curl 方式 + MCP tool 方式 并存
改为: MCP tool 统一入口，SKILL.md 只负责 workflow 指导

具体:
  - 3_kb_qa → 删除 curl 指令，改为"使用 search_knowledge_base 工具"
  - 2_tb_create → 删除 curl 指令，改为"使用 get_user_task_context + create_teambition_task"
```

这样每个能力只有一个入口，AI 不需要纠结。

#### 方案 B：强化路由规则（治标）

在每个 skill 描述中增加**互斥触发条件**：

```markdown
# 任务分析助手 ← 改名为更精确的名字
触发条件：用户明确说"分析/评估/查看任务情况"
不触发条件：用户说"绩效"、"达标"、"排单" → 这些属于绩效分析助手

# 绩效达标分析助手
触发条件：用户提到"绩效"、"达标"、"排单建议"、"工时差距"
不触发条件：单纯的"查看任务"不属于本助手
```

#### 方案 C：意图分类前置（架构优化）

在 AI 看到所有 skill 之前，先做一层意图分类：

```
用户输入 → 轻量分类器（关键词/规则）→ 决定激活哪个 skill 组
  → "创建" → 只加载 tb_create 相关能力
  → "分析/绩效" → 只加载 tb_analysis 和 perf_analysis
  → "搜索/问答" → 只加载 kb_qa 和 kb_search
  → "服务器" → 只加载 server_ops
```

#### 方案 D：动态 Skill 加载（长线方案）

不是一次性把所有 skill 塞给 AI，而是让 AI 根据用户意图**自己决定什么时候加载哪个 skill**：

```
Claude Code 的 skill 机制本身就是这个思路：
  - skill 不预加载，AI 在处理用户请求时自主判断是否需要
  - 通过 skill 的 description 做匹配
  - 只加载当前任务相关的 1-2 个 skill
```

### 11.5 当前的实际情况评估

| 问题 | 严重程度 | 当前状态 |
|------|---------|---------|
| Skill 和 MCP 功能重叠 | ⚠️ 中 | 存在但尚未造成严重问题（curl 和 MCP 都可工作） |
| Skill 间边界模糊 | ⚠️ 低 | 6 个 skill 数量不多，功能差异尚可区分 |
| 双轨制造成的不确定性 | ⚠️ 中 | 同一能力两种入口，行为可能不一致 |
| 缺少选择失败的兜底 | 🔴 需关注 | 没有"不确定时反问用户"的机制 |

### 11.6 设计原则总结

**Agent 工具设计的黄金法则**：

```
1. 一个能力，一个入口
   → 不要同时有 curl 版本和 MCP 版本

2. 触发条件要互斥
   → 用户的一句话只能匹配到最多一个 skill

3. 越少越好
   → 5 个精准的 skill 比 20 个模糊的好得多

4. 描述比实现重要
   → AI 靠描述选工具，描述写不好=工具用不对

5. 失败要有兜底
   → AI 不确定时应该反问，而不是硬选
```

### 11.7 面试回答模板

> 当前系统有 6 个 Skills 和 4 个 MCP 工具，确实存在功能重叠的风险。比如创建任务有两种方式——走 SKILL.md 的 curl 调 API，或者直接调 MCP 的 create_teambition_task。AI 可能选错入口，导致行为不一致。
>
> 解决方案是"一个能力一个入口"——让 MCP 统一承载可执行工具，SKILL.md 只负责工作流指导。同时在 skill 描述中增加互斥触发条件，确保用户一句话只命中一个 skill。
>
> Agent 工具设计有一个黄金法则：5 个精准的 skill 比 20 个模糊的好得多。AI 靠描述选工具，描述质量决定选择质量——这不是技术问题，是产品设计问题。

**更精确的定位**：

> 我是一个以 **AI 赋能** 为核心、面向 **B 端企业场景**、具备 **机器人/智能制造行业知识** 的 AI 产品经理。

### 12.4 我的差异化优势

**这恰好是一个稀缺组合**：大多数 AI PM 要么懂 AI（但不懂行业），要么懂行业（但不懂 AI）。两者的交叉点正是解决方案型 AI PM 的核心竞争力。

**如果你面的是"解决方案型"岗位**（如机器人行业 AI 方案）：

>
> 解决方案型 AI PM 的壁垒不在技术深度，而在"知道客户的真实痛点是什么，AI 能在哪个环节产生最大价值"——我的行业经验让我能做出这个判断。

## 十三、AI 解决方案前景 & 四类 PM 横向对比

> 面试官会问：你为什么选这个方向？这个方向有前途吗？和 XX 比怎么样？

### 13.1 AI 解决方案的前景

#### 市场判断：中短期爆发，长期分化

```
当前阶段（2025-2027）：AI 解决方案的黄金窗口
  ├── 企业有 AI 焦虑，愿意花钱试
  ├── 大模型能力快速提升，能解决的场景越来越多
  └── 但自建 AI 团队成本高、风险大 → 外包给解决方案商

中期（2027-2029）：分化
  ├── 头部方案商 → 产品化，做成行业 SaaS
  ├── 腰部方案商 → 被平台吞噬（大厂免费 AI 能力挤压）
  └── 尾部方案商 → 退化为纯人力外包

长期（2029+）：剩者为王
  └── 活下来的方案商都有不可替代的行业数据壁垒
```

**结论：AI 解决方案方向有前景，但窗口期有限——必须在 2-3 年内从"项目交付"升级为"产品交付"。**

#### 为什么 AI 解决方案不是伪需求

| 论据 | 说明 |
|------|------|
| **企业不会自己搭 RAG** | 技术上能做，但缺乏 AI 人才 + 评测体系 + 迭代经验 |
| **行业数据壁垒** | 通用大模型不懂行业术语，需要行业知识 + 行业数据微调 |
| **合规和安全** | 很多行业（医疗、金融、军工）数据不能上公有云，需要私有化部署方案 |
| **集成复杂度** | AI 不是独立的，要和企业现有系统（ERP、OA、MES）打通 |

#### 风险

| 风险 | 说明 |
|------|------|
| **大厂降维打击** | 钉钉/飞书/企微免费送 AI 能力，挤压中小方案商 |
| **大模型能力跃升** | 如果 GPT-5 级别的模型"开箱即用"解决了 80% 的需求，方案商的价值大幅缩水 |
| **定制化陷阱** | 每个客户需求不同 → 项目越做越多 → 利润率越来越低 → 变成 IT 外包 |
| **人才流失** | 优秀的 AI 人才更愿意去大厂或 AI 创业公司，方案商难以留住 |

### 13.2 AI 解决方案 vs SaaS

| 维度 | AI 解决方案 | 传统 SaaS |
|------|-----------|-----------|
| **交付模式** | 项目制为主，定制化程度高 | 产品制为主，标准化程度高 |
| **收入模式** | 一次性项目费 + 运维费 | 订阅制，持续收入 |
| **规模化** | 难，每个客户都要适配 | 易，一套产品多客户复用 |
| **毛利率** | 30-50%（人力成本高） | 70-90%（边际成本低） |
| **护城河** | 客户关系 + 行业知识 | 产品体验 + 网络效应 |
| **增长曲线** | 线性（人多→项目多） | 指数型（产品好→用户多→数据多→产品更好） |

**关键区别**：SaaS 是产品思维，解决方案是服务思维。AI 解决方案的终局应该是"从服务中提炼产品"——把足够多的项目经验抽象成标准化产品。

```
AI 解决方案的进化路径：

第一阶段：纯项目制（每个客户定制，赚辛苦钱）
     ↓
第二阶段：半产品化（80% 标准 + 20% 定制，规模化起步）
     ↓
第三阶段：行业 SaaS（开箱即用，少量配置即可上线）
     ↓
终局：行业 AI 平台（客户自己配置，方案商提供底座）
```

**判断一个 AI 解决方案公司是否值得去的标准**：看它处在第几阶段。如果永远是第一阶段，就是高级外包，天花板很低。

### 13.3 四类 PM 横向对比

#### 全景对比表

| 维度 | AI 产品经理 (Native) | AI 解决方案 PM | 机器人产品经理 | AGV 解决方案 |
|------|---------------------|----------------|---------------|-------------|
| **产品形态** | C 端 AI 产品（聊天/生成） | B 端 AI 定制方案 | 硬件 + 软件产品 | 硬件 + 系统集成方案 |
| **核心竞争力** | 模型体验设计 | 行业理解 + AI 落地 | 硬件工程 + 场景理解 | 系统集成 + 项目管理 |
| **技术门槛** | 中（prompt、评测） | 中高（AI + 行业） | 高（硬件、嵌入式、运动控制） | 中（系统集成） |
| **AI 依赖度** | 极高（AI 就是产品） | 高（AI 是核心组件） | 低（AI 是附加能力） | 极低（核心是硬件和调度） |
| **收入模式** | 订阅/按量 | 项目 + 运维 | 硬件销售 + 软件 License | 项目总包 |
| **毛利率** | 70-90% | 30-50% | 40-60% | 20-40% |
| **天花板** | 极高（全球市场） | 中高（行业市场） | 中高（设备市场） | 中（项目规模） |
| **稳定性** | 中（技术迭代快） | 中高（行业需求稳定） | 高（制造业刚需） | 高（仓储物流刚需） |
| **AI 冲击风险** | 低（站在风口） | 中（大厂挤压） | 低（硬件壁垒高） | 极低（物理世界） |
| **代表公司** | OpenAI、月之暗面 | 第四范式、行业 ISV | 海康机器人、极智嘉 | 迦智、快仓、海柔 |

#### 详细分析：机器人产品经理

```
做什么：
  定义 AGV/AMR 的产品规格（载重、速度、导航方式）
  管理硬件产品生命周期（研发→量产→迭代）
  对接供应链、生产、品控

核心能力：
  ✅ 硬件工程理解（机械、电子、嵌入式）
  ✅ 工业产品思维（可靠性、成本、量产）
  ✅ 场景理解（工厂/仓储的物流流程）

与 AI 的关系：
  弱相关。机器人产品经理现在不需要懂 AI。
  但趋势是 AI 在渗透——视觉导航、智能调度、预测性维护。
  未来 3-5 年，懂 AI 的机器人 PM 会成为稀缺品。

✅ 优势：硬件壁垒高，AI 替代不了，行业需求稳定增长
❌ 劣势：离 AI 远，如果未来方向是 AI PM，转型成本高
```

```
做什么：
  根据客户工厂/仓库需求，设计 AGV 系统方案
  选型、画布局图、算效率、写方案书
  项目管理：交付、调试、验收

核心能力：
  ✅ 方案设计能力（layout 规划、效率测算）
  ✅ 项目管理能力（多部门协调、进度管控）
  ✅ 客户沟通能力（挖掘需求、讲方案）

与 AI 的关系：
  几乎无关。AGV 解决方案是系统工程，核心是
  物流规划和项目管理，AI 目前帮不上什么忙。

✅ 优势：行业刚需（仓储自动化持续增长），经验越老越吃香
❌ 劣势：重复性高、出差多、和 AI 几乎不沾边
⚠️ 中年危机：干了 5 年 AGV 方案，除了行业经验，技术积累有限
```

#### AI PM vs 机器人 PM 的未来交汇点

```
当前（2025）：
  AI PM ──────────────────── 机器人 PM
    │                            │
    │  几乎无交集                  │
    │                            │

3 年后（2028）：
  AI PM ──────┬────── 机器人 PM
              │
         AI + 机器人交汇：
         • 视觉导航 AI 化
         • 机器人调度 AI 优化
         • 预测性维护 AI 诊断
         • 数字孪生 + AI 仿真
```

### 13.4 选择题：你应该走哪条路？

**用三个问题自测**：

| 问题 | 如果答案是"是"→ | 建议方向 |
|------|----------------|---------|
| 你享受做产品还是做项目？ | 产品 → AI PM / 机器人 PM；项目 → AI 解决方案 / AGV 方案 |
| 你想离技术多近？ | 越近越好 → AI PM；保持距离 → AGV 方案 |
| 你更看重天花板还是稳定性？ | 天花板 → AI PM；稳定性 → 机器人 PM / AGV 方案 |

**结合你的背景（机器人行业 + AI 落地经验）**：

```
最优路径：AI 解决方案 PM（机器人/智能制造方向）
  ├── 利用了现有优势：行业知识 + AI 能力
  ├── 踩中了趋势：制造业 AI 化是确定性方向
  └── 差异化明显：懂机器人又懂 AI 的 PM 很少

次优路径：AI 赋能型 PM（去大厂 SaaS 产品）
  ├── AI 能力可迁移，天花板更高
  └── 但放弃了机器人行业的先发优势

备选路径：机器人 PM（偏 AI 方向）
  └── 如果大模型在机器人领域爆发，你是最佳人选
```

### 13.5 面试回答模板

**问：AI 解决方案前景怎么样？**

> AI 解决方案正处于 2-3 年的黄金窗口期——企业有 AI 焦虑但自建成本高，愿意为方案付费。但长期看，只会做定制化交付的方案商会被大厂免费 AI 能力挤压。真正的价值在于从项目经验中抽象出产品——比如我们现在的知识库 RAG 系统，内部验证成熟后就可以包装成制造业知识库 SaaS。
>
> AI 解决方案的终局不是"做更多的项目"，而是"从项目中提炼出可复用的产品"。

**问：AI PM 和机器人 PM 你怎么选？**

> 如果只看眼前，机器人 PM 更稳定——硬件壁垒高，AI 替代不了。但我认为 3-5 年内 AI 会渗透到机器人领域的各个环节——视觉导航、智能调度、预测性维护。到那时，既懂机器人又懂 AI 的 PM 会极度稀缺。我现在做的就是把这两个能力同时建立起来，卡位这个交汇点。

**问：你为什么不做纯 AI 产品（AI Native）？**

> AI Native 产品的竞争已经白热化——几百家公司做 AI 聊天、AI 搜索、AI 写作。但 B 端 AI 落地——尤其是制造业、机器人行业的 AI 应用——才刚刚开始。我不需要在最卷的赛道里和 100 个 PM 竞争，我在一个几乎没人做的交叉点上建立壁垒。这个选择的本质不是"哪个方向更热"，而是"哪个方向我的优势最大"。

### 13.6 一句话总结

> "AI Native PM 做的是让 AI 本身成为商品，AI 解决方案 PM 做的是让 AI 帮客户解决实际问题。前者赚的是技术红利，后者赚的是行业 Know-how 的钱。技术红利会过期，行业 Know-how 只会越来越值钱。"

## 十四、AI Agent 平台型 PM（新赛道）

> 你的朋友在天宽科技做 AI Agent PM，经常对接华为、荣耀——这是什么方向？前景如何？

### 14.1 这是什么类型的 AI PM？

**定位：AI 平台型 PM 的一个新兴子类 —— AI Agent 平台 PM。**

```
之前我们讨论的四象限：

AI Native ─── AI 平台 ─── AI 赋能 ─── AI 解决方案
                                ↑              ↑
                              你在这里      你的一部分

现在补充第五类：

AI Agent 平台 PM ← 你朋友在这里
  ├── 既有 AI 平台属性（做的是让别人搭 Agent 的平台）
  ├── 也有 AI 解决方案属性（为大客户定制 Agent 方案）
  └── 是当前资本市场最热的方向之一
```

**天宽科技的业务模式推测**：

```
天宽科技 → 企业级 AI Agent 平台
  ├── 底层：AI Agent 开发框架（类似 Dify/Coze 的企业版）
  ├── 中间：预置行业 Agent 模板（客服、销售、IT运维...）
  └── 上层：为大客户（华为、荣耀）做定制化 Agent 方案

PM 日常工作：
  • 定义 Agent 平台的 tool/plugin 体系
  • 设计 Agent 编排和工作流引擎
  • 对接华为/荣耀等大客户，挖掘 Agent 落地场景
  • 管理 Agent 效果评估和迭代
```

### 14.2 这类 PM 的核心特征

| 维度 | AI Agent 平台 PM | 你的方向 (AI 赋能) |
|------|-----------------|-------------------|
| **产品形态** | 开发者平台/工具 | 已有产品内的 AI 功能 |
| **用户** | 开发者 + 企业客户 | 终端业务用户 |
| **输出** | Agent 搭建能力（给别人用） | Agent 应用实例（自己用） |
| **核心技能** | 开发者体验 + 生态建设 | 场景挖掘 + 功能设计 |
| **商业模式** | 平台订阅 + 定制项目 | 增值功能 |
| **典型动作** | 定义 API、写文档、建模板市场 | 做评测、跑实验、嵌入工作流 |

**一句话区别**：你做的是把 AI 用起来，他做的是让别人能把 AI 用起来。

### 14.3 职业发展前景

#### 优势

| 优势 | 说明 |
|------|------|
| **赛道红利** | 2025-2026 是"企业 AI Agent 落地元年"，市场需求爆发 |
| **大客户背书** | 对接华为/荣耀的项目经验 → 简历含金量极高 |
| **技术成长快** | 做平台能接触到最前沿的 Agent 架构（Multi-Agent、MCP、A2A 协议） |
| **天花板高** | 平台型 PM 的产品思维和技能可迁移到任何公司 |
| **薪资溢价** | 这个方向的 PM 供不应求，薪资高于传统 B 端 PM |

#### 风险

| 风险 | 说明 |
|------|------|
| **大厂碾压** | 阿里百炼、字节 Coze、腾讯元器都在做 Agent 平台，中小厂商空间被挤压 |
| **过度依赖大客户** | 如果 80% 收入来自华为/荣耀，客户集中度高，风险大 |
| **产品化难度** | 大客户定制越做越多 → 平台变成外包 → 难以标准化 |
| **技术迭代快** | Agent 架构半年一换代，平台需要不断重构 |

#### 发展路径

## 十六、n8n / Coze / Dify 三大 AI 工作流平台详解

> 2025 年 AI PM 必知的基础设施知识。这三者代表了 AI Agent 平台的三种路线。

### 16.1 一句话定位

| 平台 | 一句话 | 类比 |
|------|--------|------|
| **n8n** | 开源自动化引擎，从传统工作流向 AI Agent 延伸 | 开源的 Zapier + AI |
| **Coze (扣子)** | 字节跳动的低代码 AI Bot 搭建平台 | AI 时代的"人人都是开发者" |
| **Dify** | 开源 LLM 应用开发平台，面向开发者的 AI 中台 | 开源的 GPTs + RAG 引擎 |

### 16.2 核心差异

```
         传统自动化 ←──────────────────→ AI 原生

         n8n                     Dify              Coze
          │                       │                  │
    从 Zapier 切入           从 LLMOps 切入      从 ChatBot 切入
    逐步加 AI 能力            天生为 LLM 设计     天生为 Agent 设计
```

| 维度 | n8n | Dify | Coze |
|------|-----|------|------|
| **起源** | 传统工作流自动化 | LLM 应用开发 | AI Bot/Agent 搭建 |
| **目标用户** | 技术型运营/DevOps | 开发者/技术 PM | 非开发者/运营 |
| **开源** | ✅ Fair-code (可持续许可) | ✅ Apache 2.0 | ❌ 闭源（字节内部） |
| **部署** | 自部署 + Cloud | 自部署 + Cloud | Cloud Only |
| **AI 能力** | 后来追加（AI 节点） | 原生集成（RAG/Agent/Workflow） | 原生集成（Plugin/Workflow/Bot） |
| **生态** | 400+ 集成节点 | 模型/工具/数据集生态 | 插件商店 + Bot 商店 |
| **代码能力** | 支持代码节点 (JS/Python) | 支持代码节点 | 低代码为主 |
| **学习曲线** | 中（传统自动化思维） | 中（LLM 应用思维） | 低（拖拽 + 对话） |
| **企业功能** | 成熟（权限、审计、SSO） | 发展中（企业版） | 发展中 |
| **中国本地化** | 一般（社区驱动） | 良好（中国团队） | 极好（字节出品） |
| **商业模式** | 开源 + 企业版 License | 开源 + 云服务 + 企业版 | 免费 + 企业版 |

### 16.3 各自深度解析

#### n8n — 自动化老兵的新战场

```
核心能力：连接一切，自动化一切

技术架构：
  n8n Core (Workflow Engine)
    ├── 400+ 原生集成节点（Gmail, Slack, DB, API...）
    ├── AI 节点（LLM, Vector Store, AI Agent）
    ├── Code 节点（JS/Python 自定义逻辑）
    └── 自托管 or Cloud

AI 相关能力（后来追加）：
  • LLM 节点：调用 OpenAI/Anthropic/本地模型
  • AI Agent 节点：基于 LangChain 的 Agent 执行
  • Vector Store 节点：对接 Pinecone/Qdrant 等向量库
  • 文本处理：分块、嵌入、检索
```

**适合什么场景**：
- 企业内部的自动化流程（审批、通知、数据同步）
- 需要连接大量 SaaS 工具的场景
- 对数据安全要求高、需要自部署的企业

**不适合什么场景**：
- 纯 AI 应用开发（太重，不如 Dify 灵活）
- 非技术人员使用（学习曲线较陡）
- 需要中国本地化生态的场景

**PM 视角评价**：n8n 的护城河是 **400+ 连接器生态 + 成熟的自动化引擎**。但它是在传统产品上加 AI，不是 AI Native——如果 AI Agent 成为主流，它可能被 AI Native 的平台取代。

---

#### Coze (扣子) — 让 AI 开发民主化

```
核心能力：零代码搭建 AI Bot，发布到多渠道

技术架构：
  Coze 平台
    ├── Bot 构建器（人设、Prompt、知识库）
    ├── 工作流编辑器（可视化拖拽）
    ├── 插件商店（搜索、绘图、数据查询...）
    ├── 知识库（上传文档，自动 RAG）
    ├── 变量/数据库（持久化记忆）
    └── 多渠道发布（抖音、飞书、微信、Web...）

AI 能力（原生）：
  • 多模型支持（豆包、Kimi、GLM、DeepSeek...）
  • 内置 RAG（上传文档即可问答）
  • 代码解释器
  • 多 Agent 模式
  • 定时任务 / 触发式运行
```

**适合什么场景**：
- 快速搭建客服 Bot、营销 Bot、企业内部助手
- 运营/市场人员自己动手做 AI 应用
- 需要快速验证 AI 想法（MVP）

**不适合什么场景**：
- 复杂的开发级 AI 应用（灵活性不足）
- 私有化部署需求（目前 Cloud Only）
- 需要精细控制 LLM 行为（Prompt 被平台封装）

**PM 视角评价**：Coze 的最大优势是 **字节生态 + 零门槛**。但它的问题是"上限低"——简单的东西很好做，复杂的东西做不了。长期看，它可能吃掉"长尾 AI 应用"市场（大量简单的小 Bot），但企业级定制市场还是要靠 Dify 这样的平台。

---

#### Dify — 开发者的 AI 应用工场

```
核心能力：LLMOps 全流程平台，从 Prompt 到 Agent 到监控

技术架构：
  Dify 平台
    ├── 应用编排（ChatBot / Agent / Workflow / Text Generator）
    ├── Prompt 工程（可视化调试 + 版本管理）
    ├── RAG 管道（文档管理 → 分块 → 嵌入 → 检索 → 重排）
    ├── Agent 策略（ReAct / Function Call / 自定义）
    ├── 工作流（条件分支、并行、迭代、代码节点）
    ├── 模型管理（接入 OpenAI / Claude / 本地模型）
    ├── 日志与标注（人工标注 → 模型微调）
    └── API 发布 + 监控

AI 能力（极度全面）：
  • RAG 全链路（分块策略、检索模式、重排）
  • Agent 全模式（ReAct、FC、Multi-Agent）
  • 多模型管理（100+ 模型提供商）
  • 数据集管理（标注 → 评估 → 微调）
  • 对话日志 → 改进迭代闭环
```

**适合什么场景**：
- 企业内部知识库问答系统
- 需要精细控制 RAG 链路的场景
- 开发团队协作构建 AI 应用
- 需要私有化部署的企业

**不适合什么场景**：
- 非技术人员独立使用（有学习门槛）
- 传统自动化（不是它的强项，不如 n8n）
- 只想快速发布一个简单 Bot（太重，不如 Coze）

**PM 视角评价**：Dify 的核心壁垒是 **开源 + LLMOps 全链路覆盖**。它最接近我们之前讨论的 RAG 评测体系——从数据标注到效果评估的完整闭环。如果让我选一个平台来做知识库问答系统，Dify 是首选。它的风险在于：如果大模型能力进化到"不需要精细调教就能用"，Dify 的复杂度反而变成劣势。

### 16.5 对我们已有的 RAG 对照试验的启示

这三家平台的 RAG 实现对比我们现在的系统：

| 能力 | 我们当前 | Dify | Coze |
|------|---------|------|------|
| 分块策略 | 4 策略自适应 ✅ | 通用分块 + 自定义 | 自动分块（黑盒） |
| 检索方式 | Hybrid (FTS+Vector+RRF) | 多检索模式可选 | 内置（不可控） |
| 重排 | ❌（计划中） | ✅ 内置 Rerank | ❌ 无 |
| 评测体系 | ✅ 自建对照试验 | 日志 + 标注 | ❌ 无 |
| 模型切换 | ❌ 单模型 | ✅ 多模型 | ✅ 多模型 |

**启示**：我们的对照试验方案，在 Dify 上可以直接实现——换模型、加重排、改检索策略，都是配置级别的事情。这说明我们的设计和业界最佳实践是一致的。

如果用 Dify 来做我们的知识库问答，可以省掉 80% 的开发工作。但关键差异在于——自己开发可以控制评测体系和迭代节奏，用平台则受限于平台的能力边界。

### 16.6 面试会怎么问

**"你了解 n8n / Dify / Coze 吗？有什么区别？"**

> 这三家代表了 AI 工作流的三种路线。n8n 是从传统自动化向 AI 延伸，强在连接器生态，适合需要打通大量 SaaS 工具的企业。Coze 是字节的低代码 AI Bot 平台，零门槛、强在分发渠道，适合快速搭建简单 AI 应用。Dify 是开源的 LLMOps 平台，RAG 全链路最完整，适合需要精细控制的开发团队。
>
> 如果让我选一个做我们现有的知识库 RAG 系统，我会选 Dify——它的 RAG 管道设计和我们的对照试验方案完全一致，说明我们的方法论与业界最佳实践对齐。但自建的优势在于评测体系可以完全自定义，不受平台限制。

**"你觉得 Coze 会替代 Dify 吗？"**

> 不会。它们面向不同用户——Coze 面向"想用 AI 但不想学技术"的人，Dify 面向"想精细控制 AI 行为"的开发者。就像 Wix 不会替代 AWS，低代码不会替代专业工具。Coze 吃的是长尾市场（大量简单 Bot），Dify 吃的是中腰部市场（企业级 AI 应用）。两者的竞争交集很小。

### 16.7 一句话总结

> "n8n 是自动化老兵学 AI，Coze 是让所有人玩 AI，Dify 是让开发者造 AI。一个从过去走向未来，一个从未来走向大众，一个让未来可编程。"

### 17.2 当前系统 → Coze：能迁什么？不能迁什么？

```
✅ 可以迁到 Coze 的：
  • 知识库文档上传（PDF/Markdown/TXT）
  • 问答 Bot 搭建（Prompt + 知识库 + 工作流）
  • 发布到飞书/钉钉/微信（Coze 的优势）

❌ 迁不了的：
  • 自定义分块策略（Coze 是黑盒分块）
  • FTS + 向量混合检索的精细调参
  • 自建评测体系（Coze 无评测能力）
  • TB 任务数据融合（需自定义插件）
  • 私有化部署（Coze Cloud Only）

⚠️ 可以但受限的：
  • 嵌入模型选择（仅支持 Coze 内置的几种）
  • RAG 效果调优（能调的参数很少）
  • 多知识库管理（不如自建灵活）
```

**结论**：Coze 适合做一个"快速原型"或"对外发布的轻量 Bot"，不适合替代当前的生产系统。如果你要给老板展示一个"AI 知识库助手"的 Demo，Coze 半天就能搭出来。但要替代现在的生产系统——做不到。

### 17.3 自建 vs 平台的优劣对比

| 维度 | 自建系统 | Dify | Coze |
|------|---------|------|------|
| **分块策略** | ⭐⭐⭐⭐⭐ 4策略自适应 | ⭐⭐⭐ 通用分块 | ⭐⭐ 黑盒 |
| **检索可控性** | ⭐⭐⭐⭐⭐ 全链路代码级控制 | ⭐⭐⭐⭐ 配置级控制 | ⭐⭐ 有限配置 |
| **评测能力** | ⭐⭐⭐⭐⭐ 自建 TREC 标准框架 | ⭐⭐⭐ 日志+标注 | ⭐ 几乎无 |
| **重排** | ❌ 待开发 | ✅ 开箱即用 | ❌ 无 |
| **多模型** | ⭐⭐ 手动切换 | ⭐⭐⭐⭐⭐ 100+ 模型 | ⭐⭐⭐⭐ 内置主流 |
| **数据安全** | ⭐⭐⭐⭐⭐ 完全内网 | ⭐⭐⭐⭐ 可私有部署 | ⭐⭐ Cloud Only |
| **业务集成** | ⭐⭐⭐⭐⭐ TB数据+权限 | ⭐⭐⭐ API集成 | ⭐⭐ 插件开发 |
| **开发成本** | 🔴 高（从零造轮子） | 🟡 中（配置+少量开发） | 🟢 低（零代码） |

| **维护负担** | 🔴 全部自己维护 | 🟢 平台维护 | 🟢 平台维护 |

**核心 trade-off**：

```
自建：控制力 ↑↑↑  开发成本 ↑↑↑  天花板 ↑↑↑
Dify：控制力 ↑↑   开发成本 ↑    天花板 ↑↑
Coze：控制力 ↑     开发成本 ↓    天花板 ↓

中间路线（推荐）：Dify 做底座 + 自建评测体系 + 自建数据同步管道
  → 享受平台的基础设施红利（RAG管道、多模型）
  → 保留核心差异化的控制权（评测、分块策略、业务集成）
```

### 17.4 自建系统的真正优势（面试加分项）

很多人会说"自建灵活"，但你要能说清楚**灵活在哪些具体地方**：

| 能力 | 自建能做到 | 平台做不到 |
|------|-----------|-----------|
| **钉钉文档自动同步** | 定时拉取 → 解析 → 分块 → 嵌入，全自动 | 需手动上传 or 自建同步脚本 |
| **4 策略自适应分块** | structured/meeting/table/text 四套逻辑 | 通用分块，无文档类型感知 |
| **TREC Pooling 评测** | 三路检索合并 → LLM 标注 → 人工复核 | Dify 有日志标注，但无 Pooling |
| **TB 任务数据融合** | 知识库 + TB 任务 → LLM 综合 | 需额外开发，无法配置实现 |
| **流程完全内网** | 文档不出内网，API 走内部代理 | Dify 可私有部署，Coze 不行 |

**面试时这样答**：

> 我评估过 Dify，它确实能覆盖 80% 的 RAG 需求。但我们有两个能力是平台做不到的：第一，钉钉文档的自动增量同步——文档更新后自动重新分块嵌入，这在 Dify 上需要额外开发。第二，TREC 标准的评测体系——三路检索 Pooling + LLM 标注，这是平台没有的。第三，TB 任务数据和知识库数据在 LLM 上下文中的融合——这是业务特有的需求。
>
> 如果让我重来一次，我会用 Dify 做 RAG 底座（省掉嵌入、检索、生成的基础设施开发），但保留自建的评测体系、数据同步管道和业务集成层。这样既享受了平台的红利，又保住了差异化的控制权。

### 17.6 面试会怎么问

**"你现在的 RAG 系统，如果迁移到 Dify 要多久？有什么代价？"**

> 纯技术迁移大约 1 周——数据导出、RAG 配置、API 对接。但真正的代价不是迁移时间，而是我们会失去三个关键能力：钉钉文档的自动增量同步、TREC 标准的评测体系、TB 任务数据和知识库的上下文融合。这些是平台做不到的。
>
> 如果让我决策，我会用 Dify 做 RAG 底座来降低开发成本，但保留自建的评测体系、数据同步和业务集成层——用平台的通用能力，保自己的差异化能力。

**"作为 PM，你怎么和算法工程师分工？"**

> 我负责"定义什么是好"——构建评测体系、设计测试集、定义评估指标。算法工程师负责"怎么做到好"——实现技术方案、优化性能。但有一点 PM 不能外包：Bad Case 分析。算法看技术指标，PM 看用户场景——同一个 bad case，算法会说"向量相似度不够"，PM 会说"用户问的是导航精度，但系统返回的是导航控制器参数——虽然语义相关但不是用户想要的"。这是两种完全不同的视角，而 PM 的视角是不可替代的。

**"有了 Coze/Dify，还需要自建 RAG 吗？"**

> 取决于你的需求在不在平台的"能力天花板"之下。如果你的需求是标准的知识库问答——上传文档 → 提问 → 回答——Coze 和 Dify 都能做得很好。但一旦你需要定制分块策略、需要自建评测体系、需要融合业务数据、需要自动数据同步——你就撞到了平台的天花板。
>
> 我的建议是：先用 Dify 搭原型，验证可行性。如果 Dify 能满足 80% 需求且天花板够高，就用平台。如果撞到了天花板，再把核心模块自建。不要一上来就自建——那是没必要的重复造轮子。

### 17.7 思维模型总结

```
PM 做技术决策的三个问题：

Q1: 这个需求是"标准需求"还是"差异化需求"？
    标准 → 用平台（Dify/Coze）
    差异 → 自建

Q2: 这个需求的核心价值是"快速验证"还是"长期迭代"？
    快速验证 → 用平台（半天出 Demo）
    长期迭代 → 自建（精细控制）

Q3: 团队有没有足够的工程资源？
    有 → 自建核心模块 + 平台辅助
    没有 → 平台为主 + 自建差异化模块

最佳实践：
  平台做底座（省钱省时间）
  + 自建做差异化（保核心竞争力）
  = ROI 最高的方案
```
