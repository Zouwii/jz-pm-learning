## Q1: AI Agent 的本质是什么？Harness 是什么？

> **一句话**：AI Agent = LLM + 工具 + 自主决策循环。Harness 是 Agent 的"操作系统"——在你们的系统中就是 ttyd 终端 + Claude CLI + Skills 工作区。

### Agent 的本质

传统 LLM 调用是"一问一答"：用户输入 → 模型输出 → 结束。

Agent 的模式是"自主多步执行"：

```
用户给目标 → Agent 自主规划步骤
  → 步骤1: 调用工具A（比如搜索知识库）
  → 步骤2: 分析结果，发现不够，换策略再搜
  → 步骤3: 调用工具B（比如创建任务）
  → 步骤4: 综合所有信息，输出最终结果
```

**核心区别**：普通 LLM 是被动回答，Agent 是主动规划和执行。

### Agent 的三要素

| 要素 | 说明 | 你们的实现 |
|------|------|-----------|
| **规划能力** | 分解目标为步骤 | SKILL.md 定义的流程 + Claude CLI 自主决策 |
| **工具调用** | 操作外部系统 | curl（知识库检索）、文件读写（draft.json）、钉钉 API |
| **记忆/上下文** | 记住历史交互 | 工作区文件（AI_TASK_CONTEXT.md）、会话历史 |

### Harness = Agent 的执行环境

Harness 给 AI 一个"操作系统"。在你们的系统中，具体形态是 **ttyd 终端 + Claude CLI + Skills 工作区**：

```
用户通过 Web 界面打开 AI 终端
  → ttyd 提供浏览器内的终端会话
  → Claude CLI 作为 Agent 运行在终端中
  → Skills 目录下的 SKILL.md 定义 Agent 的行为规则
  → Agent 可以执行 curl（查知识库）、读写文件（draft.json）、调用 API
```

以 TB 任务创建为例，Agent 的执行流程：
1. 读取 AI_TASK_CONTEXT.md 了解用户上下文
2. 一问一答收集：标题 → 工时类型 → 背景 → 产出 → 时间
3. 自动生成规范化的需求描述和产出清单
4. 写入 draft.json
5. 用户确认后，后端调用钉钉 API 创建真实任务

这就是 Agent 的实际应用——不是聊天机器人，而是能操作真实业务系统的自主执行体。

**面试回答模板**：
> Agent 的本质是"LLM + 工具 + 自主决策循环"。我们的 TB 任务创建就是一个典型 Agent——它不是简单问答，而是引导式多步交互：收集标题、工时、背景，自动生成规范描述，确认后调用钉钉 API 创建真实任务。整个过程是 Agent 自主规划和执行的。

## Q2: RAG 是什么？有哪些替代方案？各有什么优劣？

> **一句话**：RAG（检索增强生成）= 先检索相关文档片段，再让 LLM 基于片段生成回答。它的核心 trade-off 是"用检索换记忆"——检索可能漏，但知识更新快、可溯源。

### 替代方案全景对比

| 方法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **RAG** | 检索文档片段 → LLM 生成 | 知识更新快、可溯源、成本低 | 检索质量不可控、可能漏召回 |
| **Fine-tuning（微调）** | 用企业文档训练专属模型 | 知识内化，不需要检索 | 更新需重新训练、成本高、无法溯源 |
| **Prompt Engineering** | 把所有知识写在 system prompt 里 | 简单直接 | 上下文窗口有限，知识量大时不可行 |
| **纯关键词搜索 + LLM** | FTS 检索 + LLM 生成 | 简单 | 语义理解弱，同义词匹配不了 |
| **Graph RAG** | 用知识图谱替代向量检索 | 实体关系推理强 | 构建成本高，维护复杂 |
| **Agentic RAG** | Agent 多步检索，自主判断充分性 | 检索质量更高 | 延迟增加，多次 LLM 调用 |

### RAG 的 7 个常见问题（诚实面对）

| 问题 | 说明 | 你们的处理 |
|------|------|---------|
| 检索质量不可控 | 召回不全或不准 | 对照试验量化，TREC 标准评测 |
| 分块策略影响大 | 切太碎丢上下文，切太大精度降 | 4 策略自适应分块 |
| LLM 忽略检索结果 | 模型"自作主张" | System prompt 约束 + 来源引用 |
| 无法回答推理问题 | RAG 是"找答案"不是"推理" | 复杂问题用 Agent 多步检索 |
| 知识更新延迟 | 文档更新 → 分块 → 嵌入有延迟 | 手动触发同步，后续做增量更新 |
| 上下文窗口浪费 | 检索 20 条，可能 5 条有用 | 加 reranker 精排 |
| 同义词/术语不匹配 | 用户说的和文档写的不一样 | Embedding 语义检索弥补 |

### RAG vs Fine-tuning 决策框架

```
知识频繁更新？ → 是 → RAG
                → 否 → 考虑 Fine-tuning

需要溯源引用？ → 是 → RAG
                → 否 → Fine-tuning 可以

数据量大（远超上下文）？ → 是 → RAG
                        → 否 → Prompt 直接塞

需要推理能力？ → 是 → 二者结合（RAG 检索 + Fine-tuned 模型推理）
```

**面试金句**：
> "RAG 不是银弹。它的核心 trade-off 是用检索换记忆——检索可能漏，但知识更新快、可溯源。Fine-tuning 是用训练换记忆——知识内化更准确，但更新成本高。没有最好，只有最合适的场景。"

## Q3: AI 大模型和传统工程化的边界在哪里？怎么判断该不该用 AI？

> **一句话**：先用工程方法解决 80% 的确定性问题，再用 AI 解决 20% 的模糊问题。反过来——先上 AI 再补工程——会导致不可控的质量问题。

### 核心判断框架

| 维度 | 适合工程化 | 适合 AI |
|------|-----------|---------|
| **输入是否确定** | 确定的（if-else 能穷举） | 开放式的（自然语言、图像） |
| **规则是否明确** | 明确的（业务规则、计算公式） | 模糊的（需要理解语义） |
| **是否需要创造性** | 不需要（标准化流程） | 需要（内容生成、推理） |
| **容错要求** | 零容错（金融交易） | 可容错（搜索、推荐） |
| **数据特征** | 结构化、标签化 | 非结构化、多模态 |
| **更新频率** | 低频（业务规则稳定） | 高频（知识持续变化） |

### 具体场景判断

| 场景 | 用 AI？ | 理由 |
|------|---------|------|
| 计算员工工时 | ❌ 工程化 | 规则明确、零容错 |
| 理解文档内容回答问题 | ✅ AI | 非结构化、开放式查询 |
| 审批流程流转 | ❌ 工程化 | 规则确定，不需要"理解" |
| 自动生成周报摘要 | ✅ AI | 需要理解+生成，容错较高 |
| 数据库 CRUD | ❌ 工程化 | 确定性高，AI 反而可能出错 |
| 语义搜索 | ✅ AI | 同义词、口语化，规则穷举不了 |
| 图像质检（合格/不合格） | ⚠️ 看情况 | 规则明确→传统 CV；模糊标准→AI |

### 你们 RAG 系统的实践

```
✅ 工程化（确定性高）：
  - FTS 关键词检索 → 精确匹配，零幻觉
  - 文档同步管线 → 标准工程
  - 4 策略分块 → 规则明确
  - RRF 融合排序 → 经典算法

✅ AI（需要理解和生成）：
  - 向量语义检索 → 理解同义词
  - LLM 综合生成 → 多文档信息合成

⚡ 协作边界：
  - 检索：工程粗筛（快）+ AI 精筛（准）
  - 生成：AI 生成 + 工程约束（来源引用、格式规范）
```

### 实用判断公式

```
适合用 AI = 
  输入不确定（自然语言/图像/音频）
  × 输出不需要 100% 精确
  × 人工做成本高/速度慢
  × 有足够的测试数据验证效果

四个全满足 → 用 AI
一个不满足 → 慎重
两个不满足 → 大概率不该用
```

**面试金句**：
> "先用工程方法解决 80% 的确定性问题，再用 AI 解决剩余 20% 的模糊问题。反过来——先上 AI 再补工程——往往会导致不可控的质量问题。"

## Q4: 大模型的"幻觉"是什么？怎么理解和缓解？

> **一句话**：幻觉 = 模型生成了看似合理但实际不存在的内容。RAG 系统的幻觉根因是检索质量——检索不到的，模型就会"编"。缓解靠三层：检索提质量、生成做验证、呈现加置信度。

### 幻觉在 RAG 系统中的三种表现

| 类型 | 表现 | 根因 |
|------|------|------|
| 检索失败型 | 没有召回相关内容 → 模型"编造" | 检索质量不足 |
| 过度推理型 | 检索到部分内容 → 模型补充了文档中没有的细节 | LLM 的生成惯性 |
| 错误关联型 | 跨文档综合 → 模型错误关联不相关信息 | 检索片段之间缺乏关系建模 |

### 你们当前的缓解措施

- System prompt 明确要求："资料不足时明确告知，不编造"
- 检索结果附带来源引用，用户可追溯验证
- Temperature 设为 0.3（降低随机性，但无法消除幻觉）

### 更完善的幻觉防控体系

```
层级1 — 检索侧（源头防）
  检索后评估：用 Self-RAG 思路，检索完先判断是否充分
  不够 → 重新检索，不强行生成
  
层级2 — 生成侧（过程控）
  答案验证：生成后，用另一个 prompt 验证是否与检索内容一致
  不一致 → 回退，标注"信息不足"
  
层级3 — 呈现侧（用户知）
  置信度标注：对低置信度回答标注"仅供参考"
  引用精确到 chunk：不是引用整个文档，而是具体段落
```

### 如何判断"是不是为了 AI 而 AI"

三个自检问题：

| 问题 | 判定 |
|------|------|
| 这个问题不用 AI 能不能解决？ | 能 → AI 可能是多余的 |
| AI 方案比非 AI 方案在哪个维度更好？ | 说不清 → 为 AI 而 AI |
| AI 的隐性成本（幻觉、延迟、维护）是否被接受了？ | 没想过 → 不够诚实 |

防"锤子思维"的 PM 方法：
1. 先定义问题，再选工具。不是先选了 AI 再找场景
2. 每个 AI 功能配套"不用 AI 的降级方案"
3. 用指标说话——AI 版不比非 AI 版好，就不上

**面试金句**：
> "幻觉的根因不是模型'爱撒谎'，而是检索质量不够。检索不到的，模型就会补。所以我们的核心工作是提升检索质量——用 TREC 标准评测、做对照试验，从源头减少幻觉。"

## Q5: 精度和召回率在 RAG 系统里怎么理解和平衡？

> **一句话**：召回率 = "该找的都找到了吗"，精度 = "找到的都是有用的吗"。RAG 优化策略是——先多召回保召回率，再用 reranker 精排提精度。

### 概念速查

| 概念 | 含义 | 极端表现 |
|------|------|---------|
| **精度（Precision）** | 检索到的内容中，有多少是相关的 | 精度高 = 每条都有用，但可能漏 |
| **召回率（Recall）** | 所有相关内容中，检索到了多少 | 召回高 = 基本不漏，但噪声多 |
| **MRR** | 第一个相关结果排第几 | 衡量排名质量 |
| **nDCG** | 综合相关性和排名位置 | 更全面的排名指标 |

### 你们 RAG 优化中的精度-召回策略

```
当前：检索 top-20 → 融合 → 取 top-8
  → 保精度（宁可少，不要错）

对照试验：用 Recall@5 / MRR / nDCG 三项指标
  → 量化评测，不是拍脑袋

加 reranker（计划中）：
  → 先粗召回 20 条（保召回）
  → 再精排到 8 条（提精度）
  → 不牺牲召回的提精度
```

### Precision @ K vs Recall @ K 的应用场景

| 场景 | 侧重 | 原因 |
|------|------|------|
| 客服知识库 | 精度优先 | 答错比不答更糟 |
| 法律文书检索 | 召回优先 | 漏掉关键判例是灾难 |
| 企业内部问答 | 平衡 | 既要准（别浪费用户时间），又要全（别漏关键信息） |

**面试回答模板**：
> "我们在 RAG 优化中同时监控 Recall@5、MRR 和 nDCG。策略上采用'先多召回再精排'——用 bge-small 做粗召回保召回率，用 reranker 做精排提精度。这比简单调 top_k 更有效，因为它在两个维度上独立优化。"

## Q6: AI 行业有哪些关键发展节点？

> **一句话**：从 2017 年 Transformer 架构奠定基础，到 2022 年 ChatGPT 引爆，再到 2025-2026 年 Agent 从实验走向生产——AI 行业经历了"架构突破 → 规模验证 → 产品爆发 → Agent 落地"四个阶段。

### 大模型关键时间线

| 时间 | 事件 | 意义 |
|------|------|------|
| 2017.06 | Google 发布 Transformer 论文 | 奠定现代 LLM 架构基础 |
| 2020.05 | OpenAI 发布 GPT-3 (175B) | 展示大模型 emergent ability |
| 2021.06 | GitHub Copilot 发布（基于 Codex） | AI 编码助手进入主流 |
| 2022.11 | **ChatGPT 发布** | 🔥 引爆全球 AI 浪潮 |
| 2023.03 | GPT-4 + Claude 发布 | 多模态、推理、安全对齐 |
| 2023.06 | Agent 概念爆发（AutoGPT, BabyAGI） | Agent 范式进入公众视野 |
| 2024-2025 | DeepSeek-V3、Qwen、GLM 等国产模型崛起 | 中文能力 + 成本优势 |
| 2025-2026 | MCP 协议、AI IDE（Cursor/Windsurf）成熟 | Agent 从实验走向生产 |

### Agent 概念演进

Agent 不是新概念——1980 年代就在研究。关键是 **2023 年是 LLM-based Agent 的爆发点**：

- 2023.03：AutoGPT 发布，展示 LLM 自主分解目标执行多步任务
- 2023.04：BabyAGI、AgentGPT 涌现
- 2023.06：LangChain Agent 模块成熟
- 2024-2025：Agent 从玩具走向生产（客服 Agent、编码 Agent、数据分析 Agent）

### Claude 和 Codex 的关键时间点

- **Codex**：2021.08 发布，2021.10 GitHub Copilot 上线——AI 编码助手的开端
- **Claude**：2023.03 发布，2023.07 Claude 2 支持 100K 上下文
- **Claude Code**：2025 年推出，Agent 能力直接嵌入开发环境

### 已验证的落地场景

| 场景 | 案例 | 成熟度 |
|------|------|--------|
| 编码助手 | GitHub Copilot, Cursor | ⭐⭐⭐⭐⭐ |

# 第二部分：RAG 系统设计

## Q7: 你们的 RAG 系统是怎么设计的？为什么自建而不是用钉钉 AI？

> **一句话**：从 10 个钉钉知识库自动同步 → 4 策略分块 → bge-small 嵌入 → pgvector + FTS5 混合检索 → RRF 融合 → LLM 流式生成。自建是因为钉钉 AI 跨不了 workspace、检索质量黑盒、无法融合业务数据。

### 系统架构全景

```
钉钉知识库（10 个工作区）
  → 自动同步（文档树 → 下载 → 解析为 Markdown）
  → 智能分块（4 策略自适应：技术文档/会议/表格/文本）
  → 嵌入向量化（bge-small-zh-v1.5, 512d → pgvector）
  → 混合检索（FTS5 关键词 + 向量语义 → RRF 融合）
  → LLM 生成回答（检索 chunk + 用户问题 → SSE 流式返回）
```

### 为什么不用钉钉 AI？（五个维度对比）

| 维度 | 钉钉 AI | 自建 RAG |
|------|---------|----------|
| 跨知识库聚合 | ❌ 单 workspace | ✅ 10 库统一检索 |
| 检索质量可控 | ❌ 黑盒，等平台更新 | ✅ 全链路可控，A/B 实验驱动 |
| 业务数据融合 | ❌ 仅钉钉文档 | ✅ 知识库 + TB 任务数据融合 |
| 数据安全 | ⚠️ 经钉钉服务器 | ✅ 内网私有化 |
| 长期成本 | 高（按量付费） | 低（自有 infra） |

核心痛点举例：用户问"导航精度和到点自学习的关系"，答案散落在 3 个不同 workspace 里，钉钉 AI 只能在单个 workspace 内搜。

### 为什么不用纯工程化方案？

| 方案 | 为什么不够 |
|------|-----------|
| **纯关键词搜索** | 用户不会精确概括关键词。"车走偏了怎么回事"和文档里的"AGV 走偏 轮速差 编码器"词面完全对不上 |
| **结构化数据库** | 企业知识天然非结构化——PRD、会议纪要、设计文档不可能统一建模 |
| **人工 Wiki** | 10 个知识库持续更新，手动维护不可接受 |
| **规则匹配** | 问题空间开放式，无法穷举。维护成本随知识增长线性上升 |

### 工程和 AI 不是对立，是互补

```
工程侧：FTS 精确匹配 | 4策略自适应分块 | RRF 融合排序 | 钉钉 API 文档同步
AI 侧： bge-small 语义检索 | LLM 综合生成回答
```

**面试金句**：
> "钉钉 AI 是通用搜索，我们做的是领域知识引擎。前者告诉你'哪里可能有答案'，后者直接给你答案。"
> "工程化方案让用户适应系统，AI 让系统适应用户。这是范式选择，不是技术选型。"

## Q8: 模型调用链路是怎样的？数据安全吗？

> **一句话**：Flask 后端 → one-api 内部代理 → DeepSeek 等外部模型服务商。不发送源代码，只发送知识库 markdown 文档片段。可逐步加固到私有化部署。

### 调用链路

```
用户请求 → Flask 后端
  → 检索本地知识库（MySQL + pgvector）
  → 拼接 prompt（system prompt + 检索文档片段 + 用户问题）
  → HTTP POST → one-api 代理（内部部署）
  → 转发到模型服务商（DeepSeek）
  → SSE 流式返回
```

关键参数：
- 模型：`deepseek-v4-flash`
- Temperature：0.3
- Max tokens：4096
- one-api 统一代理，API key 集中管理

### 数据安全逐环节分析

| 环节 | 数据暴露 | 风险 | 现状 |
|------|---------|------|------|
| 知识库文档内容 | 作为 prompt 发送给 LLM | ⚠️ 中 | 仅 markdown 文档片段 |
| 源代码 | **不发送** | ✅ 低 | - |
| TB 任务数据 | 检索到的标题/状态 | ⚠️ 中 | 限检索范围 |
| 用户身份 | 不发送给 LLM | ✅ 低 | - |
| API Key | 存储于 config.json | 🔴 高 | ⚠️ 生产需改用密钥管理 |

### 加固路径

```
当前：文档内容 → one-api 代理 → 外部模型服务商
升级1：one-api 挂私有化部署的 DeepSeek 开源模型，数据不出内网
升级2：敏感文档脱敏/摘要后再发送
升级3：按知识库分级——机密走本地，普通走云端
```

**面试回答模板**：
> 我们通过 one-api 内部代理统一管理模型调用。目前风险可控——不发送源代码，只发送知识库 markdown 文档。如果安全要求更高，可以在 one-api 后面挂私有化部署的开源模型，数据完全不出内网。这是一个可以逐步加固的过程。

## Q9: 上下文窗口溢出了怎么办？

> **一句话**：当前做简单截断（8000 token 上限）。最优方案是加 reranker 精排——从 20 条粗召回中精挑 8 条，保证进 prompt 的都是最相关的。

### 当前处理

```python
total_tokens = 0
for r in results:
    tk = r.get("token_count") or len(content) // 2
    if total_tokens + tk > _MAX_CONTEXT_TOKENS:
        break  # 超限即丢弃
    parts.append(content)
    total_tokens += tk
```

问题：后面的 chunk 直接丢弃，8000 token 对 deepseek-v4 过于保守。

### 五种处理策略对比

| 策略 | 做法 | 优劣 |
|------|------|------|
| **Rerank 精排** ⭐推荐 | 粗召回 20 → reranker 精排到 8 | 保证最相关内容进 prompt |
| Summary 压缩 | LLM 先摘要再拼接 | 保信息但多一次 LLM 调用 |
| 动态窗口 | 按模型实际能力调上限 | 利用大窗口，减少截断 |
| 分层检索 | 先搜摘要→命中后加载全文 | 类似"目录→正文" |
| Map-Reduce | 分批生成→合并 | 适合超长文档 |

你们的对照试验加 reranker，本身就是对上下文利用率的优化。

## Q10: 端到端响应速度怎么样？怎么优化？

> **一句话**：当前 2-10 秒。检索 ~200-500ms，LLM 生成是主要耗时。已做 SSE 流式输出，用户可边等边看。缓存是下一步。

### 延迟构成

| 环节 | 耗时 | 优化空间 |
|------|------|---------|
| SQLite FTS 关键词 | ~10-50ms | 小 |
| pgvector 向量检索 | ~100-300ms | 加索引 |
| RRF 融合 | ~5ms | 小 |
| LLM 首 token | ~500-2000ms | 流式已做 |
| LLM 完整生成 | 2-10s | 流式已做 |

### 已做优化
- SSE 流式输出：用户不用等全部生成
- 状态提示："检索本地向量知识库" → "调用模型生成回答"

### 待做优化
- 检索缓存：相同 query 秒回
- 预加载 embedding 模型：减少首次延迟

**面试话术**：

## Q11: 多 Skill 和 MCP 并存时，AI 会不会选错工具？

> **一句话**：会的。根本原因是 LLM 的"工具选择"是语义匹配，不是逻辑判断。解决靠三点：统一入口、互斥触发条件、失败反问兜底。

### 你们的现状

**Skills（6 个 SKILL.md）**：server_ops、keyword_extract、tb_analysis、perf_analysis、tb_create、kb_qa

**MCP Tools（4 个）**：get_user_task_context、create_teambition_task、search_knowledge_base、get_workhour_summary

### 三个典型问题

**问题 1：功能重叠，AI 可能选错入口**

| 用户想做的事 | 可以走的路 | 风险 |
|-------------|-----------|------|
| 创建任务 | SKILL.md curl **vs** MCP tool | 走 curl 可能绕过 MCP 校验 |
| 搜知识库 | SKILL.md curl **vs** MCP tool | 返回格式不一致 |
| 分析任务 | tb_analysis **vs** perf_analysis | 边界模糊 |

**问题 2：Skill 描述模糊，触发条件重叠**

用户说"帮我看看任务情况"——tb_analysis 和 perf_analysis 都可能触发。

**问题 3：双轨制造成不确定性**

同一能力两个入口（curl vs MCP），AI 行为取决于它先看到哪个。

### 解决方案

| 方案 | 做法 | 类型 |
|------|------|------|
| **A. 统一入口** ⭐推荐 | MCP 承载可执行工具，SKILL.md 只负责 workflow | 治本 |
| B. 互斥条件 | 每个 skill 加"触发条件"和"不触发条件" | 治标 |
| C. 意图分类前置 | 先分类意图 → 再加载对应 skill 组 | 架构优化 |
| D. 动态加载 | AI 自主判断何时加载哪个 skill（Claude Code 自带能力） | 长线 |

### Agent 工具设计的五条黄金法则

```
1. 一个能力，一个入口 → 不要同时有 curl 版和 MCP 版
2. 触发条件要互斥 → 用户一句话只命中一个 skill
3. 越少越好 → 5 个精准 > 20 个模糊
4. 描述比实现重要 → AI 靠描述选工具
5. 失败要有兜底 → 不确定时反问，不硬选
```

**面试回答模板**：
> 当前确实存在功能重叠风险——创建任务有 curl 和 MCP 两种方式。解决方案是"一个能力一个入口"：让 MCP 统一承载可执行工具，SKILL.md 只负责工作流指导。同时 skill 描述要加互斥触发条件。Agent 工具设计的核心原则是：5 个精准的 skill 比 20 个模糊的好得多，AI 靠描述选工具，描述质量决定选择质量——这不是技术问题，是产品设计问题。

## Q12: n8n / Coze / Dify 有什么区别？各适合什么场景？

| 维度 | n8n | Dify | Coze |
|------|-----|------|------|
| **起源** | 传统工作流自动化 | LLM 应用开发 | AI Bot/Agent 搭建 |
| **目标用户** | 技术型运营/DevOps | 开发者/技术 PM | 非开发者/运营 |

### 三选一决策框架

```

需要在钉钉/飞书/微信发布 AI Bot？ → Coze（字节生态 + 多渠道）
需要做企业内部 RAG 系统？ → Dify（RAG 全链路最完整）
需要私有化部署？ → n8n 或 Dify（都开源）
团队没技术人员？ → Coze（唯一真零代码）
```

**面试金句**：

## Q14: 用户真的会用 AI 工具吗？怎么推动落地？

> **一句话**：企业内部工具的宿命是"做了不一定有人用"。推动落地靠三点：嵌入工作流（别让用户另开页面）、解决真痛点（聚焦 3 个高频场景做到极致）、信任建设（展示来源引用 + 支持反馈）。

### 用户不用 AI 的四个原因

1. 习惯已形成（直接问同事、翻钉钉文档）
2. 不信任 AI 回答（担心编造）
3. 使用门槛（需要学怎么提问）
4. 答案不够好 → 用一次就放弃

### AI 工具 vs 当前做法

| 场景 | 当前做法 | AI 替代价值 |
|------|---------|------------|
| 查技术文档 | 钉钉搜索，逐篇翻 | 语义搜索 + 直接给答案 |
| 了解项目进度 | 问同事 / 翻 TB | AI 自动汇总 |
| 新人学习 | 问老员工 | 自助问答，减轻老员工负担 |
| 跨部门信息 | 拉群问 / 开会 | 一站式查询 |
| 创建任务 | 手动填表单 | AI 引导 + 自动生成 |

### 五步推动落地

```
1. 嵌入工作流：不要另开页面，集成到钉钉机器人、IDE 插件
2. 解决真痛点：不是"什么都能问"，聚焦 3 个高频场景做到极致
3. 信任建设：展示引用来源、支持"答得不对"反馈
4. 冷启动：找 2-3 个种子用户，优化到满意后再推广
5. 效果可见：对比"查文档 10 分钟 vs AI 30 秒"，让价值可感知
```

> 关键认知：AI 工具不是替代"什么都不做"，而是替代"低效的做法"。只要比当前做法好一个数量级，就有价值。

## Q15: AI 知识库只有内部提效价值吗？能商业化吗？

> **一句话**：内部提效是商业化的 MVP。这套能力本质上是"非结构化企业知识的 AI 化"，适用场景远不止一家公司。可沿三条路径商业化：企业知识库 SaaS、现场运维知识助手、行业专用 AI。

### 三层价值递进

```
第一层：内部提效（已实现）
  研发团队内用，提升文档检索和问答效率

第二层：产品化（可探索）
  打包成 SaaS，卖给有同样需求的公司
  例：制造业企业技术文档知识库

第三层：行业解决方案（远期）
  针对机器人/智能制造定制，含行业知识图谱
```

### 四条商业化路径

| 路径 | 目标客户 | 可行性 |
|------|---------|--------|
| **企业知识库 SaaS** | 有大量文档的中型企业 | ⭐⭐⭐ 技术成熟，有需求 |
| **现场运维知识助手** | 设备制造商售后团队 | ⭐⭐⭐ AGV 行业刚需 |
| **行业专用 AI** | 智能制造/物流行业 | ⭐⭐ 需行业数据 |
| **钉钉应用市场插件** | 钉钉生态企业 | ⭐⭐⭐ 渠道优势 |

**面试金句**：
> "内部提效是商业化的 MVP。先把内部体验打磨到极致，再考虑对外输出。但这套能力本质上是'非结构化企业知识的 AI 化'，适用场景远不止一家公司。"

## Q16: PM 怎么和算法工程师协作？

> **一句话**：PM 负责"定义什么是好"（评测标准、测试集、指标），算法负责"怎么做到好"（技术实现、性能优化）。唯一不能外包的 PM 工作是 Bad Case 分析——算法看技术指标，PM 看用户场景。

### 基于自建系统的协作

```
PM ──────────────────────── 算法

定义问题和目标                 实现技术方案
  "表格类文档 recall 只有 40%"    "用 bge-m3 替换 bge-small"

构建评测体系                  执行实验
  • 26条标注测试集               • 跑 A/B 代码
  • 4种查询类型分类               • 收集指标
  • Recall@5 / MRR / nDCG

分析结果，做决策               分析技术瓶颈
  "bge-m3 在技术文档 recall       "bge-m3 对长文本 dense
   提升 15%，表格仅 3%。           向量不够，建议加 sparse"
   加 reranker 后表格到 60%。
   采用 D 方案。"

制定迭代计划                  技术选型建议
  "① 上线 D 方案                 "三个方向的可行性：
   ② 补充 10 条表格测试题          ① 低风险，直接做
   ③ 调研表格专用分块"            ② 需先 PoC
                                 ③ 成本高，等①上线"
```

### PM 必须自己能做的事

| 能力 | 为什么 PM 必须会 |
|------|-----------------|
| 写评测方案 | PM 核心产出，算法只执行 |
| 构建测试集 | 算法不懂业务，不知道什么叫"好答案" |
| 分析 Bad Case | 算法看指标，PM 看用户场景 |
| Prompt 设计 | PM 的语言表达 + 业务理解 |
| 模型选型 trade-off | 成本/效果/延迟 = PM 决策 |

### PM 不需要亲自做但必须能判断的事

- 技术方案是否 over-engineer，是否解决真问题
- 一件事该花 1 天还是 1 周
- 能参与"用 bge-m3 还是 text-embedding-3"的讨论

**面试回答模板**：
> 我负责"定义什么是好"——构建评测体系、设计测试集、定义评估指标。算法负责"怎么做到好"。但有一点 PM 不能外包：Bad Case 分析。同一个 bad case，算法会说"向量相似度不够"，我会说"用户问的是导航精度，但返回的是导航控制器参数——虽然语义相关但不是用户想要的"。PM 的视角不可替代。

## Q17: AI PM 有哪些细分方向？各有什么特点？

> **一句话**：五大方向——AI Native（做 AI 产品本身）、AI 平台（让别人能搭 AI）、AI 赋能（让已有产品变智能）、AI 解决方案（帮行业用 AI）、AI Agent 平台（帮企业搭 Agent）。你的最佳卡位是 AI 解决方案（机器人/智能制造方向）。

### 五大方向全景

| 方向 | 做什么 | 代表公司 | 核心能力 |
|------|--------|---------|---------|
| **AI Native** | AI 就是产品本身 | ChatGPT, Kimi, Midjourney | 模型体验设计、prompt 交互 |
| **AI 平台** | 让开发者搭 AI 应用 | Dify, LangChain, 百炼 | 开发者体验、API 产品化 |
| **AI 赋能** | 已有产品 + AI 能力 | 钉钉AI, Notion AI, Copilot | 场景挖掘、工作流嵌入 |
| **AI 解决方案** | 行业 AI 方案落地 | 第四范式, 行业 ISV | 行业 Know-how + AI 落地 |
| **AI Agent 平台** | 企业 Agent 搭建平台 | Coze, 天宽, 澜码 | Agent 编排 + 客户方案 |

### 五大方向核心对比

| 维度 | AI Native | AI 平台 | AI 赋能 | AI 解决方案 | AI Agent 平台 |
|------|-----------|---------|---------|------------|--------------|
| 热度 | 🔥🔥🔥🔥 | 🔥🔥🔥🔥🔥 | 🔥🔥🔥 | 🔥🔥🔥 | 🔥🔥🔥🔥🔥 |
| 竞争 | 极激烈 | 激烈 | 中等 | 较低 | 激烈 |
| 你的匹配度 | ★★ | ★★★ | ★★★★ | ★★★★★ | ★★★ |

### 你的定位

```
我是一个以 AI 赋能为核心、面向 B 端企业场景、
具备机器人/智能制造行业知识的 AI 产品经理。

差异化优势：
  ✅ 机器人行业知识（导航/伺服/AGV 调度）
  ✅ AI 落地实战（RAG + Agent + MCP + 评测体系）
  ✅ 工程能力（能搭架构、能写代码）
  = 纯 AI 背景和纯行业背景的 PM 都不具备的组合
```

### 职业发展三条路径

```
当前 → AI 赋能型 PM

  ├─ 路径 1：深耕 AI 赋能 → 去大厂 SaaS（钉钉AI/飞书/Notion AI）
  ├─ 路径 2：转向 AI 解决方案 → 机器人行业 AI 方案公司
  └─ 路径 3：转向 AI 平台 → Dify/向量数据库/MCP 生态公司
```

**面试回答模板**：
> 我目前是 AI 赋能型 PM 为主，兼具解决方案型特征。我的核心竞争力不是追风口，而是在一个几乎没人做的交叉点建立不可替代性——机器人行业知识 × AI 落地实战经验。大多数 AI PM 要么懂 AI 不懂行业，要么懂行业不懂 AI，两者的交叉点恰好是解决方案型 AI PM 最需要的能力。

## Q18: AI 解决方案 PM 的前景怎么样？

> **一句话**：AI 解决方案正处 2-3 年的黄金窗口期。但长期看，只会做定制的会被大厂免费 AI 压垮。真正的价值在于从项目中提炼可复用的产品——从服务升级到产品。

### 市场判断

```
2025-2027：黄金窗口
  ├── 企业有 AI 焦虑，愿意花钱试
  ├── 大模型能力快速提升，能解决的场景越来越多
  └── 自建 AI 团队成本高 → 外包给方案商

2027-2029：分化
  ├── 头部方案商 → 产品化，做成行业 SaaS
  ├── 腰部方案商 → 被大厂免费 AI 挤压
  └── 尾部方案商 → 退化为纯人力外包

2029+：剩者为王
  └── 活下来的都有不可替代的行业数据壁垒
```

### AI 解决方案 vs 传统 SaaS

| 维度 | AI 解决方案 | 传统 SaaS |
|------|-----------|-----------|
| 交付 | 项目制，定制化高 | 产品制，标准化高 |
| 收入 | 一次性项目费 + 运维 | 订阅制，持续收入 |
| 规模化 | 难，每个客户要适配 | 易，一套多客户复用 |
| 毛利率 | 30-50% | 70-90% |
| 护城河 | 客户关系 + 行业知识 | 产品体验 + 网络效应 |

### 进化路径

```
第一阶段：纯项目制（定制，赚辛苦钱）
     ↓
第二阶段：半产品化（80% 标准 + 20% 定制）
     ↓
第三阶段：行业 SaaS（开箱即用）
     ↓
终局：行业 AI 平台（客户自配置，方案商提供底座）
```

> 判断一家 AI 方案公司是否值得去的标准：看它处在第几阶段。永远是第一阶段 = 高级外包。

### 四类 PM 横向对比（补充机器人/AGV视角）

| 维度 | AI PM (Native) | AI 解决方案 | 机器人 PM | AGV 方案 |
|------|---------------|------------|----------|---------|
| AI 依赖度 | 极高 | 高 | 低 | 极低 |
| 毛利率 | 70-90% | 30-50% | 40-60% | 20-40% |
| 天花板 | 极高 | 中高 | 中高 | 中 |
| 稳定性 | 中 | 中高 | 高 | 高 |
| AI 冲击 | 低（风口） | 中（大厂挤压） | 低（硬件壁垒） | 极低 |

**面试回答模板**：
> AI 解决方案正处 2-3 年的黄金窗口——企业有 AI 焦虑但自建成本高。但长期看，只会定制交付的会被大厂免费 AI 碾压。真正的价值在于从项目经验中抽象产品。AI 解决方案的终局不是做更多项目，而是从项目中提炼可复用的产品。

## Q20: AI PM 这个岗位的前景怎么样？

> **一句话**：AI PM 会从"特殊岗位"变成"基础能力"——就像现在 PM 都需要懂数据分析。真正稀缺的是能定义 AI 产品评估标准、能设计 Agent 工作流、能做模型选型 trade-off 的 PM。

### 核心能力变化

| 传统 PM | AI PM |
|---------|-------|
| 写 PRD | 写 Prompt 和评估标准 |
| 画原型 | 定义 Agent 行为流程 |
| 用户调研 | 构建评测数据集 |
| 竞品分析 | 模型选型评估 |
| 数据分析 | 精度/召回/延迟分析 |

### 3-5 年趋势

- AI PM 会从"特殊岗位"变成"基础能力"
- 真正稀缺：能定义评估标准、设计 Agent 工作流、做模型 trade-off 的 PM
- 最危险："只会调 API 的 AI PM"——门槛太低，无壁垒

### AI + 机器人 PM：未来交汇点

```
当前（2026）：
  AI PM ────────────────── 机器人 PM
    │                          │
    │  几乎无交集                │

3 年后（2029）：
  AI PM ──────┬────── 机器人 PM
              │
         AI + 机器人交汇：
         • 视觉导航 AI 化
         • 调度 AI 优化
         • 预测性维护 AI 诊断
         • 数字孪生 + AI 仿真

  这个交叉点上的人才极度稀缺。
```

### 你的最佳策略

```
现阶段：主攻 AI 解决方案 PM（机器人/智能制造方向）
        备选 AI 赋能型 PM（企业 SaaS）
        关注 AI Agent 平台方向

核心竞争力不是追风口，而是在交叉点建立不可替代性：
  机器人行业知识 × AI 落地实战经验
  = 未来 3-5 年最稀缺的 AI PM 画像之一
```

**面试金句**：
> "AI PM 的核心竞争力不是'会用 AI'，而是'知道 AI 的边界在哪'——什么时候该用，什么时候不该用，用了能提升多少，风险是什么。"
> "AI Native PM 做的是让 AI 本身成为商品，AI 解决方案 PM 做的是让 AI 帮客户解决实际问题。前者赚技术红利，后者赚行业 Know-how 的钱。技术红利会过期，行业 Know-how 只会越来越值钱。"
