# 到点自学习：产品化包装与 AI 路线

## 结论

这个项目不应包装成“高并发后端平台”，也不应把统计自学习直接说成 AI。

更准确的产品定位是：

> 面向 AGV/AMR 高精度对接场景的到点质量闭环产品。它把依赖实施人员反复试跑和静态调参的工作，转化为按场景持续采集、计算、审核、下发、验证和回退的数据闭环，目标是提升多车到点一致性并降低长期标定维护成本。

当前已经完成的是确定性的采集与补偿闭环。Nav 内部的 AI 应聚焦“样本是否可信、补偿是否可能收敛”；跨车辆的异常诊断、漂移预测和预防性维护属于正在建设的 AGV 云端运维平台，不能全部包装成 Nav 已有能力。

## 一、用产品语言重新定义项目

### 1. 用户与场景

当前可合理识别的用户角色如下，但具体人数和使用频率仍需本人补证据：

| 用户角色 | 核心任务 | 主要痛点 | 产品提供的能力 |
| --- | --- | --- | --- |
| 现场实施/交付 | 让多台机器人稳定对接同一工位 | 反复试跑、逐车调参、环境变化后需要重做 | 自动积累样本、按场景生成补偿、一键执行 |
| 导航研发 | 判断误差来自控制、定位、Tag 还是场景配置 | 数据分散，难复现，依赖个人经验 | 精度分析、错误记录、分发历史和样本回放 |
| 现场运维 | 发现异常后快速止损和恢复 | 自动补偿可能放大错误，现场不敢直接使用 | 全局/单点开关、置零、异常清理和回退 |
| 项目负责人 | 判断哪些车、点位和路径需要优先处理 | 缺少统一质量视图 | 按车辆、路径和误差类型聚合分析 |

### 2. 用户原来的解决方式

1. 实施人员针对每台车、每个点位反复试跑；
2. 根据经验手工写入静态补偿；
3. 现场环境、轮胎、载荷或楼层变化后重新排查；
4. 遇到异常时在日志、地图配置和导航结果之间人工比对。

原方案的问题不是“没有算法”，而是标定经验无法沉淀、不同场景容易串用、结果不可持续验证、异常发生后难以快速止损。

### 3. 产品目标

产品目标分为三层：

1. **结果目标**：改善同一场景下的多车到点一致性；
2. **效率目标**：减少人工试跑、重复标定和问题排查时间；
3. **安全目标**：保证自动生成的补偿可审核、可追踪、可禁用、可置零。

当前第三层已有较完整功能证据；前两层仍缺统一的线上指标，不能宣称已经提升了具体百分比。

### 4. 核心产品机制

```text
真实任务产生样本
      ↓
按“车—点—场景 Key”隔离数据
      ↓
判断样本是否有效、分布是否稳定
      ↓
计算补偿并限制单次变化
      ↓
人工/自动流程审核与下发
      ↓
车端按同一场景 Key 匹配并使用
      ↓
继续采集补偿后误差，验证并迭代
```

这个闭环体现了四个关键产品决策：

- 不强行拆解所有误差来源，而是围绕最终到点结果建模；
- 不用一份补偿覆盖所有情况，而是用场景 Key 明确复用边界；
- 不把“算出补偿”当成完成，而是设计采集到再验证的完整链路；
- 不追求无人控制的自动化，而是先建立开关、清理、记录和回退。

## 二、可以证明的 AI PM 能力

### 1. 问题定义

把“某台车到点不准”的技术现象，提升为“多车一致性差、标定维护成本高、经验无法复用”的产品问题。

### 2. 复杂业务建模

将机器人、点位、前置点、载荷、楼层、末姿角、有码/无码和 UUID 设计成场景边界。这里的难点不是增加字段，而是决定一份补偿在什么条件下可以安全复用。

### 3. MVP 到产品化

| 阶段 | 核心能力 | 产品意义 |
| --- | --- | --- |
| 计算能力 | 样本分组、均值/Kalman/Welford 等实验 | 验证补偿是否可计算 |
| 业务闭环 | 同步、计算、下发、车端匹配、再采集 | 验证结果能否真正生效 |
| 风险控制 | 开关、限幅、置零、异常清理、状态恢复 | 让现场敢于使用 |
| 运营工具 | Web 筛选、一键流程、历史、精度分析 | 降低使用和排查门槛 |

### 4. 数据驱动决策

算法不按“听起来是否先进”选择，而是比较：

- 小样本阶段是否稳定；
- 对 warm-up 离群点是否敏感；
- 多少轮能够收敛；
- 误差是否持续落在阈值内；
- 出错后是否容易解释和回退。

现有实验已经发现 Welford 的早期样本污染问题，因此不能把它描述成已经稳定替代旧方案。

### 5. 安全与边界意识

补偿会改变机器人实际目标位姿，属于高风险输出。产品设计必须把“计算”和“使用”解耦，并保留人工判断、全局/点位控制、限幅和回退能力。

## 三、指标体系

### 北极星指标

建议定义为：

> 启用自学习补偿后，满足到点精度阈值的有效任务占比。

这个指标同时包含效果和可用性，但目前没有统一线上数据，只能作为下一阶段定义，不能写成既有成果。

### 指标树

| 层级 | 建议指标 | 说明 |
| --- | --- | --- |
| 结果指标 | 到点误差 P50/P95、多车离散度、对接/任务成功率 | 判断最终效果 |
| 效率指标 | 单点标定工时、收敛轮次、从异常发现到处理完成时长 | 判断是否降低人工成本 |
| 覆盖指标 | 覆盖现场/机器人/点位数、有效场景 Key 覆盖率、补偿启用率 | 判断使用范围 |
| 数据指标 | 样本有效率、异常样本率、场景字段完整率 | 判断输入是否可靠 |
| 安全指标 | 异常补偿率、禁用/置零率、回退率、下发失败率 | 防止只看平均精度 |
| 使用指标 | 周活跃操作人员、一键流程使用率、建议采纳率 | 判断产品是否真正被使用 |

### 现在最该补的证据

1. 选一个正式现场、一个地图和一批稳定点位；
2. 导出补偿前后同口径样本；
3. 计算 P50/P95、标准差、任务成功率和异常率；
4. 记录人工标定次数与处理时长；
5. 保存一个成功 Case 和一个失败/回退 Case。

## 四、AI 能与哪些部分结合

### 先划清三个系统的边界

```text
Nav-Application / Nav-Manager
到点样本与补偿执行闭环
        ↓
AGV 云端运维平台（正在开发）
多车健康数据、趋势和异常事件
        ↓
Diagnosis-Agent（正在开发/验证）
检索外部证据、解释原因、形成处置建议
```

详细关系与本人在云端运维平台中的职责见：[AGV 云端运维平台：项目边界与三项目关系](./05-云端运维平台关联.md)。

### 优先级判断

| 方向 | 主要归属 | 价值 | 建议 |
| --- | --- | --- | --- |
| 样本质量与异常检测 | Nav | 高 | P0 |
| 收敛风险预测与策略推荐 | Nav | 中高 | P1 |
| 多车趋势与预防性维护 | 云端运维平台 | 中高 | 先验证数据与标签 |
| 到点异常诊断助手 | 云端运维平台 + Diagnosis-Agent | 高 | Agent V1 后延展 |
| Tag/二维码视觉质量检测 | 云端运维平台 | 中 | 有图片和标注后再做 |
| LLM 直接计算并下发补偿 | 不应归属任何层 | 低价值、高风险 | 不做 |

### 方向一：样本质量与异常检测

这是最适合首先引入的 AI/机器学习能力。

**问题**

固定阈值能识别明显异常，但难以覆盖多变量组合、渐进漂移和不同场景的正常分布差异。

**输入**

- 位置与角度误差；
- 载荷、楼层、前置点和补偿类型；
- 历史补偿及变化幅度；
- 机器人、路径和点位统计；
- 时间、版本和任务上下文。

**输出**

- 样本是否可信；
- 异常类型：单点离群、持续漂移、车辆异常、路径异常或场景配置异常；
- 风险分数和关键影响特征；
- 进入计算、挂起观察或转人工。

**推荐方案**

先从可解释的统计检测、Isolation Forest 或聚类开始，影子运行验证后再影响计算链路。这里不需要 LLM。

**验收指标**

- 已知异常召回率；
- 正常样本误杀率；
- 异常提前发现时间；
- 被人工确认的异常占比；
- 因异常样本造成的错误补偿次数。

### 方向二：到点异常诊断助手

这不是 Nav 内部优先开发的功能，而是云端运维平台产生异常事件后，由 Diagnosis-Agent 承接的上层能力。

这是最适合作为 AI PM 故事延展的功能，也能与 Management-System 的 RAG 和 Diagnosis-Agent 的证据链能力衔接。

**用户问题**

现有系统能告诉用户“哪个车辆或路径的均值、标准差、极值异常”，但不能充分解释为什么异常、下一步查什么。

**产品流程**

```text
精度分析触发异常
      ↓
确定性工具收集样本、补偿历史、地图配置、版本和相关日志
      ↓
异常检测模型给出模式与风险分
      ↓
RAG 检索错误码、SOP、技术文档和历史 Case
      ↓
LLM 只基于证据生成原因候选和处置建议
      ↓
用户确认后执行继续学习、点位整改、研发介入或禁用补偿
```

**输出格式**

- 现象摘要；
- 影响范围；
- 原因候选与置信度；
- 每个结论对应的样本、日志或文档证据；
- 推荐动作和风险提示；
- 信息不足时明确要求补充什么。

**安全边界**

- LLM 不直接修改目标位姿；
- LLM 不直接下发补偿；
- 没有证据时不得输出确定根因；
- 禁用、置零、下发等写操作必须由规则校验并人工确认；
- 原始数据、模型判断和最终操作都要留审计记录。

**验收指标**

- 根因候选 Top-1/Top-3 命中率；
- 证据引用完整率；
- 平均排查时长；
- 建议采纳率；
- 错误建议率；
- 转人工率和信息不足识别率。

### 方向三：收敛风险预测与策略推荐

不同场景的噪声和稳定性不同，统一采用相同样本数、阈值和算法并不一定合适。

AI 可以根据历史 Case 预测：

- 当前场景是否有可能在限定轮次内收敛；
- 应继续采样、调整阈值、切换算法还是暂停；
- 当前补偿变化是否存在过冲风险；
- 哪类车辆或路径更值得优先处理。

该能力初期只能作为离线推荐或影子模式。只有积累足够标签并通过回放验证后，才考虑进入自动流程。

### 方向四：漂移趋势与预防性维护

这部分已经出现在 AGV 云端运维平台 V1 需求中，属于独立在研项目，而不是 Nav 的未来功能清单。

将到点误差从“单次是否超阈值”升级为时间序列趋势：

- 某台车是否持续向同一方向漂移；
- 某条路径是否在地面、轮胎或版本变化后整体恶化；
- 某个点位是否频繁需要重新学习；
- 补偿更新频率是否异常升高。

产品输出应是巡检优先级和证据趋势，不直接宣称设备故障。

### 方向五：Tag/二维码视觉质量检测

如果能够稳定获得原始图片和人工标签，可以识别遮挡、污损、反光、角度或安装偏差，并把视觉质量与到点误差关联。没有图片数据和标注前，不将其列为近期 MVP。

## 五、推荐的 AI MVP

如果只讨论 Nav-Application，近期只做一个切口：

> 样本风险门控：在补偿计算前识别离群、warm-up 不稳定和场景分布漂移，输出“接受、挂起、继续采样或转人工”，先以影子模式运行，不直接改变补偿。

选择它的原因：

1. 直接处理现有 Welford warm-up 和离群样本问题；
2. 输入、输出和错误后果都容易定义；
3. 可以用历史样本离线回放；
4. 先影子运行，不改变高风险导航闭环；
5. 不与云端运维平台和 Diagnosis-Agent 重复建设。

### MVP 范围

只使用当前场景 Key 下的误差、补偿历史、样本顺序和稳定性统计。

只输出四种状态：

- 接受样本；
- 挂起样本；
- 继续采样；
- 暂停计算并转人工。

### MVP 不做

- 不让 LLM 计算补偿值；
- 不自动修改地图或车端参数；
- 不在 Nav 中重复建设云端健康诊断；
- 不引入复杂多 Agent；
- 不在没有评测集时追求全量上线。

## 六、分阶段路线

| 阶段 | 产品目标 | 主要交付物 | 放行条件 |
| --- | --- | --- | --- |
| Phase 0：数据基线 | 先证明现有闭环效果 | 指标口径、成功/失败 Case、P50/P95 和安全指标 | 数据可追溯 |
| Phase 1：智能识别 | 提高异常发现和样本过滤能力 | 异常检测、影子报告、人工标签 | 误杀率可接受 |
| Phase 2：策略推荐 | 降低试跑与算法选择成本 | 收敛预测、策略推荐、离线回放 | 不劣于规则 baseline |
| Phase 3：平台联动 | 将异常送入云端诊断链路 | 标准异常事件、证据查询接口 | 与云端平台数据口径一致 |
| Phase 4：受控自动化 | 对低风险动作提高自动化程度 | 审批、灰度、回滚、审计 | 真实 Case 与安全指标长期稳定 |

## 七、interview 讲法

### 30 秒产品版

> 我做的不是一个单独的补偿算法，而是一套 AGV 到点质量闭环产品。现场原来依赖实施人员逐车、逐点试跑和静态调参，我把任务数据按车、点、前置点、载荷、楼层和有码/无码场景隔离，设计了采集、计算、审核、下发、应用和再验证的闭环，并补充开关、限幅、清理、历史和精度分析控制风险。Nav 下一步 AI 重点是样本风险门控和收敛建议；跨车趋势与诊断则进入独立的云端运维平台和 Diagnosis-Agent。

### 2 分钟结构

1. 用户是谁，为什么人工静态标定成本高；
2. 为什么产品目标是多车一致性和维护效率；
3. 为什么用场景 Key，而不是一份补偿覆盖所有情况；
4. 如何从采集到再验证形成闭环；
5. 为什么要把计算、使用和回退解耦；
6. 如何用实验比较算法，而不是追求算法名词；
7. 为什么 Nav 内部先做样本门控，而把长期诊断放到云端平台；
8. 当前缺少哪些业务指标，准备如何补齐。

### 被问“这是不是 AI 项目”

> 当前核心不是大模型，而是统计学习和确定性工程闭环，我不会为了包装把它说成生成式 AI 项目。Nav 内部先用异常检测提高样本安全性；多车长期趋势进入云端运维平台；RAG/Agent 再基于日志、配置和历史 Case 辅助诊断。三个层次各自解决不同问题，最终控制仍交给确定性规则和人工审批。

## 八、事实边界

- “用户角色”和“北极星指标”是基于现有系统形成的产品化定义，真实用户人数、频率和指标值仍需补充；
- 已完成的是跨仓确定性闭环、产品操作和算法实验；
- Nav 的异常检测和收敛预测属于规划；云端运维平台已形成 V1 需求分解但仍在开发；Diagnosis-Agent 仍在验证；
- 不把 Ops、MapMaster、导航框架或控制器说成个人开发；
- 不把统计自学习直接等同于大模型 AI；
- 没有统一线上数据前，不宣称精度、成功率或人效提升了具体比例。
