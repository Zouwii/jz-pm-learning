# Management-System

> 2026-07-31 范围修正：旧 RAG 文档、旧 26 题测试集和旧实验仅作为 legacy baseline。当前虽已获得约 55G 图文知识库（5,427 份 Markdown、19,886 张图片），但 RAG v2 不做全量多模态，收敛为“研发项目与模块知识助手”：优先处理人员、任务、方案、项目节点、验收表和代码仓库文档，图片只保留回链。新范围必须重新设计测试集和评测。

## 一句话

面向本体开发团队的 2B 数据与 AI 工作台，把钉钉知识库、TB 任务和组织数据连接起来，提供知识问答、任务辅助和管理分析。

## 这个项目证明什么

这是 AI PM 主项目。旧版本证明我做过完整 RAG 和评测闭环；RAG v2 要进一步证明我能发现旧方案的数据基础和范围都不成立，并从“全量知识库”收敛到可验证的研发项目知识场景：

- 从内部真实痛点中定义产品问题；
- 判断工程方案、RAG 和 Agent 的能力边界；
- 搭建数据同步、分块、混合检索、对话和 MCP 全链路；
- 建立测试集与离线指标，用实验而不是感觉做优化决策；
- 同时考虑权限、部署、性能和用户工作流。

## 项目讲述主线

### 背景与问题

团队知识散落在多个钉钉知识库和 TB 任务中。员工检索成本高，任务描述不规范；管理者难以快速获得结构化信息。钉钉原生能力存在跨空间、检索黑盒和业务数据融合限制。

### 方案

```text
钉钉知识库 / TB 数据
        ↓
同步、解析、四类自适应分块
        ↓
FULLTEXT/FTS + bge-small 向量检索
        ↓
RRF 融合 + Cross-Encoder reranker
        ↓
带来源引用的 LLM 对话
        ↓
Skills / MCP 执行业务动作
```

### Legacy 评测闭环

- 用三路检索 Pooling 构建 26 条测试问题；
- 形成 135 个相关 chunk 标注，测试集无空题；
- 使用 Recall@5、MRR、nDCG@5 衡量检索质量；
- 对比 Hybrid RRF baseline 与 Cross-Encoder reranker；
- legacy 数据上的可核验结果：Recall@5 从 34.13% 提升到 59.60%，约提升 25.5 个百分点；
- 最终选择 `bge-reranker-base`，原因是服务器 CPU 约 1 秒/query，效果与成本更平衡。

### 我的产品判断

1. 先优化检索质量，再讨论 Prompt，因为检索错误是上游根因。
2. 先用小而可解释的测试集建立 baseline，再逐步扩大在线反馈。
3. 不盲目换大 embedding；reranker 在当前数据上收益更明确。
4. 平台提供基础能力，自建部分聚焦内部数据、权限和工作流差异。

## 三种讲法

### 30 秒

我先完成过一版钉钉知识库 RAG 和离线评测。拿到约 55G 原始数据后，我没有直接做全量多模态，而是重新从用户问题定义范围：面向研发新员工和项目成员，重点回答谁做过什么、相关任务和方案在哪里、项目何时验收，以及模块设计文档在哪里。V1 用结构化查询处理人员、节点和验收事实，用 Hybrid RAG 检索任务、方案和仓库文档，图片只保留回链。旧结果只作为 legacy baseline，新范围需要重新评测。

### 2 分钟

按“用户问题 → legacy 方案与评测 → 为什么全量范围不成立 → 三类核心场景 → 结构化查询与 RAG 分工 → canary 与新评测 → 事实边界”展开。

### 5 分钟

在 2 分钟版基础上加入：

- Markdown 结构、`@人员` 关系、时间节点与表格行组；
- 项目、任务、方案与代码仓库文档的统一元数据；
- 结构化查询、Hybrid RRF 与 reranker；
- checksum 幂等重建、ACL 和灰度迁移；
- 新测试集中的人员关系、项目事实、方案与模块文档问题；
- 尚未完成的 canary、在线指标和用户采纳闭环。

## 风险与口径

- legacy 26 题规模较小，只能证明旧链路中的局部方向；
- legacy 标注使用 LLM 辅助，需要人工复核；
- `34.13%→59.60%` 只能作为旧数据 baseline，不能宣传为 RAG v2 结果；
- 新范围尚未完成 canary 和新评测，RAG v2 当前状态必须描述为“重构中”；
- 不把离线 Recall 或字段提取准确率直接等同于用户满意度。
