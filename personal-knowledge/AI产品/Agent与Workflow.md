# Agent 与 Workflow：如何划分边界

## 核心结论

一个系统不需要为了使用 Agent 而把所有步骤都交给大模型。更合理的方式通常是：

> 以确定性 Workflow 为主，只在路径不确定的关键节点引入 Agent。

## Workflow 适合做什么

当任务步骤、顺序、输入和输出可以提前定义时，优先使用 Workflow 或普通代码，例如：

- 下载和整理材料；
- 调用固定接口或连接设备；
- 检查版本和运行状态；
- 裁剪数据、正则扫描和提取字段；
- 执行规则或 Playbook；
- 保存过程数据并生成标准化产物。

这些步骤使用确定性程序更稳定、便宜、可测试，也更容易审计和重试。

## Agent 适合做什么

Agent 的主要价值是处理无法提前穷举的决策：

1. **理解非结构化输入**：把自然语言现象转成可验证的问题方向。
2. **动态选择路径**：根据阶段性结果决定下一步调用什么工具、检查什么证据。
3. **管理多个假设**：提出候选原因，逐项验证和排除，而不是只执行一条固定链路。
4. **判断证据充分度**：区分已确认、较可能、需要人工和数据不足，避免把相关性直接当作因果关系。
5. **处理证据冲突**：比较不同来源的证据强度，判断是真冲突，还是同一因果链的不同环节。
6. **决定追问或转人工**：信息不足时提出最小必要问题；遇到高风险动作或无法闭环的判断时交给人工。

## Agent、Engine 与 Playbook

- **Agent 是大脑和调度者**：理解目标、选择路径、组织假设、判断证据和决定下一步。
- **Engine 是手和眼**：稳定执行数据采集、处理、规则扫描、工具调用和结果落盘。
- **Playbook 是经过验证的操作知识**：描述触发条件、候选原因、区分证据、检查步骤和输出要求。

Agent 不应重复实现 Engine，也不应脱离 Playbook 和真实证据直接猜测结论。

## 判断是否需要 Agent

设计功能前可以依次提问：

1. 路径能否提前完整定义？如果可以，优先使用 Workflow。
2. 普通规则能否覆盖主要情况？如果可以，先做规则和 Playbook。
3. 下一步是否依赖刚刚获得的非结构化证据？如果是，才考虑 Agent。
4. Agent 的选择是否能够被验证、回退和人工接管？如果不能，暂时不要自动化。
5. 引入 Agent 后，相比 Workflow 是否实际提升了任务完成率、材料完整度或处理效率？需要用真实 Case 验证。

## 在诊断类产品中的应用

诊断系统可以采用以下结构：

```text
固定 Workflow：采集 → 预处理 → 规则扫描
                         ↓
                已知模式：执行 Playbook
                         ↓
                未知模式：Agent 管理和验证假设
                         ↓
                证据不足：追问或转人工
                         ↓
                输出带证据的结论
```

因此，诊断产品更准确的定位通常不是“完全自主 Agent”，而是“确定性诊断 Workflow + Agent 决策节点”。
