## 一、文档概述

### 1.1 这是什么

一个 **AI Agent**，接在 Claude Code 上，自动完成技术支持问题的端到端诊断。

```
用户输入问题
  → Agent 判断来源（内网机器人 / TB任务 / 远程现场 / 本地日志）
  → 自动采集数据（SSH拉日志、下载附件、解压）
  → 规则引擎提取异常（error/warn/错误码/时间窗口裁剪）
  → 搜索外部证据（钉钉知识库、GitLab代码、历史案例）
  → 综合推理，出诊断报告
```

### 1.2 一句话说清

> 技术支持工程师不用再手动 ssh、翻日志、搜文档——告诉 Agent 问题现象，它自动完成采集、分析、检索、出报告。

### 1.3 不是 Agent vs 是 Agent

以前用 bash/Python 脚本也能做日志分析，但这个项目是 **Agent** 的原因：

| | bash 脚本 | 这个 Agent |
|---|---|---|
| **理解症状** | 关键词匹配 "旋转"→导航类 | 自然语言理解 "到点后转了3圈就停了，地图显示还在路径上" |
| **证据关联** | 列出所有 error 行 | 激光 timeout + nav-manager REACH_ROTATE + 版本不一致 → 因果链 |
| **路由决策** | 硬编码优先级 | 一个问题涉及导航+安全+设备，Agent 动态决定先查哪个 |
| **结论判断** | 规则说啥就是啥 | 证据够不够闭环？要不要再查文档？Agent 反思 |
| **人机协同** | 报 "缺少信息" | 精准追问："问题发生在几点？给一个时间就能锁定时段" |

### 1.4 与现有系统的关系

| 系统 | 关系 |
|------|------|
| jz-claude-skills 仓库 | Agent 本体代码在这里，包含编排 skill + CLI 引擎 |
| management-system | 通过 ttyd 网页终端为用户提供访问入口（端口 5433） |
| robot-peek / robot-diagnosis 等 | Agent 调用的子 skill，负责专项分析 |
| 钉钉知识库 / GitLab | Agent 的外部证据来源 |

## 二、为什么要做

### 2.1 当前问题

| 问题 | 现状 |
|------|------|
| **排查效率低** | 出问题后，工程师手动 ssh 连车 → tail 日志 → grep 关键词 → 翻钉钉文档 → 翻 GitLab 代码，一套下来 30 分钟起步 |
| **经验靠人脑** | 老工程师知道 622002 是激光通信超时，新人不知道，每一代都要重新学 |
| **文档没人维护** | 排查完了就完了，经验不沉淀，下次同样问题又从头查 |
| **skill 太多记不住** | 仓库有 10+ 个 skill，工程师不知道该调哪个、怎么串联 |

### 2.2 做完之后

- 输入一个 IP 或 TB 链接，Agent 自动跑完采集→分析→检索→报告
- 错误码自动映射到根因，不用人脑记
- 每次诊断自动尝试搜索钉钉知识库中的已有经验
- 诊断完了自动生成知识库沉淀草稿

## 四、三阶段路线图

```
一阶段              二阶段               三阶段
发现异常      →     理解异常        →    能解决异常
规则匹配      →     知识库推理      →    代码仓库溯源
grep/regex     →    语义搜索        →    git blame
error/warn     →    指纹匹配        →    因果链
            →    根因映射        →    修复方案
            →    置信度量化      →    自动闭环
```

### 4.1 一阶段（当前）

**能力：发现异常**

- 7 个 CLI 子命令（run / resume / analyze / status / export / list / init-config）
- 4 种输入来源（TB 任务 / 内网机器人 / 远程现场 / 本地日志）
- SSH 自动巡检机器人（系统信息、版本、进程、ROS、错误日志）
- 按正则提取异常行（fatal / error / warn）和错误码
- 6 种问题分类（导航旋转 / 导航 / 安全 / 任务链路 / 设备传感器 / 通用）
- 70+ 条日志-模块映射，按问题类型自动排日志优先级
- 时间窗口裁剪（问题时间前后 5→10 分钟）
- 6 项固定规则深层归因（jstate告警、定位异常、版本不一致、进程停止等）
- 搜索钉钉知识库文档（最多 5 篇）+ GitLab 代码
- 本机 token 匹配历史案例
- 生成 6 种产物（report.md / human-handoff.md / knowledge-draft.md / context.json / status.json / next-prompt.md）

### 4.2 二阶段（规划中）

**能力：理解异常** — 引入知识库

- 错误码 → 根因映射（622002 自动返回故障名、触发条件、常见根因）
- 日志指纹匹配（多关键词组合匹配已知问题模式）
- 多信号交叉推理（版本不一致 + 定位异常 → 因果链）
- 跨机器案例共享，全量语义搜索
- 置信度量化（从 likely/need_human 变为 84%）
- 修复方案闭环，跟踪→反馈→优化

### 4.3 三阶段（规划中）

**能力：能解决异常** — 接入代码仓库

- 错误码 → git blame 定位源码 → 关联 MR
- 版本差异 → diff 分析 → 因果链
- 配置参数可解释（这个值为什么这么设？）
- 时间线对齐（日志 ↔ 代码发布 ↔ 部署）
- 自动创建 Issue、关联 MR
- 报告从"建议研发查看"变为"根因在 nav-manager/src/speed_arbiter.cpp:156，方案A/B，已有 draft MR"

## 五、Agent 架构

```

  │
  ▼
┌─ diagnosis-orchestrator (SKILL.md) ───────┐  ← Agent 大脑

│  决定：闭环 / 追问 / 人工介入              │
├───────────────────────────────────────────┤
│  Python CLI (diagnosis_cli.py, 3276 行)   │  ← Agent 手和眼
│  SSH 巡检 / TB下载 / 正则提取 / 时间裁剪  │     确定性操作，不调模型
│  文件扫描 / 错误码提取 / 模块映射          │
├───────────────────────────────────────────┤
│  子 skill 池（9 个已有 skill）             │  ← 专项工具
│  robot-diagnosis / task-engine-troubleshoot│
│  device-log-analyzer / robot-model-config  │
│  dingtalk-docs / gitlab-operator / ...     │
└───────────────────────────────────────────┘
```
