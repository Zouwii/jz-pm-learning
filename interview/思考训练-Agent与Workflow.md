# 思考训练：Agent 与 Workflow 如何划分边界

## 核心结论

一个系统不需要为了使用 Agent 而把所有步骤都交给大模型。更合理的方式通常是：

> 以确定性 Workflow 为主，只在路径不确定的关键节点引入 Agent。

## Workflow 适合做什么

当任务步骤、顺序、输入和输出可以提前定义时，优先使用 Workflow 或普通代码，例如：

- 下载和整理材料；
- 调用固定接口或连接设备；
- 检查版本和运行状态；
- 裁剪数据、正则扫描和提取字段；
- 执行规则或 Playbook；
- 保存过程数据并生成标准化产物。

这些步骤使用确定性程序更稳定、便宜、可测试，也更容易审计和重试。

## Agent 适合做什么

Agent 的主要价值是处理无法提前穷举的决策：

1. 理解非结构化输入；
2. 根据阶段性结果动态选择路径；
3. 管理并验证多个候选假设；
4. 判断证据充分度和冲突；
5. 决定追问、降级或转人工。

## Agent、Engine 与 Playbook

- **Agent 是大脑和调度者**：理解目标、选择路径、组织假设并判断证据；
- **Engine 是手和眼**：稳定执行采集、处理、规则扫描、工具调用和结果落盘；
- **Playbook 是经过验证的操作知识**：描述触发条件、候选原因、区分证据、检查步骤和输出要求。

Agent 不应重复实现 Engine，也不应脱离 Playbook 和真实证据直接猜测结论。

## 判断问题

1. 路径能否提前完整定义？可以则优先 Workflow；
2. 普通规则能否覆盖主要情况？可以则先做规则和 Playbook；
3. 下一步是否依赖刚获得的非结构化证据？是则考虑 Agent；
4. Agent 的选择能否被验证、回退和人工接管？不能则暂不自动化；
5. 引入 Agent 后是否实际提升任务完成率、材料完整度或处理效率？需要用真实 Case 验证。

## interview 练习题

> 面对一个业务需求，你如何判断它适合使用 Agent、确定性 Workflow，还是普通规则系统？
